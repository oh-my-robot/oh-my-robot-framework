`E:\MyDocument\NUEDC\workspace\base_on_omr\oh-my-robot-framework`（分支 `feature/boot-ota-research`），且其 **2026-09-16 追加 Q-12..Q-16，决策正文 = ADR-0025 (boot_decision_data_and_jump_contract)**。

**boot 侧已锁定、本底座必须服务的决策**（**对齐优先于创新**）：

| 决策 | 内容 | 对本底座的含义 |
|---|---|---|
| **entry 布局** | **32B 定长**：`seq / activeSlot / state / bootCount / imageVersion / flags / reserved / crc32`；**CRC 覆盖决策字段全集** | 本底座只需提供"写单位对齐 + 擦除单位"即可支撑；**不要再发明第二套提交格式** |
| **写序铁律** | **提交标记最后写**；**永不擦最新有效份**；erase 态（全 0xFF）**须显式判无效** | 与本设计 §4.3 的"有效性判定必须是合取"一致——**已由 boot 侧定，无需重议** |
| **擦除归属** | **写者只向"已擦副本" program，自身不做擦除**；擦除归**引导侧**；不变式 ⇒ **至少 3 份** | ⚠️ **本底座必须同时支持两种模式**：meta = "写者不擦"；**日志环 = 运行期擦除**（环形轮转）。这直接决定操作面不能只给"program + 已擦前提" |
| **算法 ID** | 命名 **canonical 变体**（CRC-32/ISO-HDLC），**芯片后端负责映射**；摘要覆盖区 4 字节对齐、长度为 4 的倍数 | 与本设计 §4.3 的错误码分层同源；若将来底座要带校验，**沿用 canonical 命名** |
| **元数据落点** | **独占可擦区域**；位置**无需与运行镜像分 bank**（K-37） | 与日志环不同：**meta 在引导期擦除**故无 RWW 问题；**日志环运行期擦除**，bank 仍重要（§F.7.1） |
| **写并发硬约束**（K-38） | RM0090 明文 "**Write-while-write operations are not allowed**"，BSY 为**全局位**，同 bank 擦/写/读全 stall | ⇒ **日志环的预擦必须与应用写入"时间错开"**——这是 E-1 方案的前提条件，不是优化项 |
| **耐久口径**（K-38） | AN3969/AN2594 逐字："A program/erase cycle consists of one or more write accesses and one page erase operation"（同周期多次 program **折 1 次**）；**retention 与每周期 program 次数无 ST 背书** | 支撑"追加式写、很少擦"的设计；但**保持性若为硬指标需自做试验** |

**⇒ 由此收窄本设计的开放项**：原 §5 中"提交标记最后写""CRC 覆盖范围""算法 ID 命名"三项**已由 boot 侧决定**，本设计直接采用，不再单列。

### 0.1 「boot meta 先只依赖本接缝」的可行性核验（2026-09-19，用户决定后）

**用户决定：要求 boot meta 先只依赖 `om_partition_*`**（不绕过它直接调 PAL）。⇒ 必须先确认这套接口在 **boot 侧的执行环境下真能跑**，否则等于把自己锁死。**核验通过；且发现该风险原本是真实的（不是假想）。**

| 检查点 | 结论 |
|---|---|
| **功能覆盖** | **够**：读/写 32B entry → `read` / `write`；擦单份副本 → `erase_range`；**判 erase 态无效 → `is_erased`**；**找 ≥3 个独立擦除单位 → `erase_unit_*`**；4 字节对齐 → `geom.writeUnit`。§0 表中"**擦除归引导侧**"正对应 §4.2 的**模式 B（写者不擦）** |
| **分层姿态** | `partition.h:9-11` 已声明逐字："可裁剪组件（非必备）——**boot/OTA/存储上层才消费**；依赖面 = flash 设备族同步面，**与 osal-none 裁剪组合兼容（本模块零 osal 依赖）**" |
| **执行环境（真风险点）** | bootloader = **osal-none**。而 `flash_sync_wait` 有一句**自锁拒绝**：`osal_thread_self() == dev->domain->wq.thread → OM_ERR_FLASH_BUSY`——**若成立，每次同步写都失败**。核验：`osal_thread_none.c:48` 与 `:52-58` 使 `thread_create` 与 `thread_self` **返回同一个单例**（看似必然自锁）；**但** `workqueue.c:196` 在坍缩形态下 `wq->thread = NULL`，且 `:199-205` **不建线程** ⇒ 比较是"**单例 == NULL**" = false ⇒ **放行**。等待侧 `work_wait_idle`（`workqueue.c:627-634`）有**已 IDLE 快速路径**，而坍缩下 `enqueue` 是**当场直调**（`workqueue.c:69-79`）⇒ 提交返回时已完成，快速路径立即返回。**⇒ bootloader 路径可用，无阻塞。** |

⚠️ **这条链上有一处已知坑（同仓回归实证）**：`workqueue.c:63-67` 记着守卫约定——`#if (OM_OSAL_PORT == OSAL_PORT_NONE)` **裸写会使两宏按 0 相等而静默坍缩**，原文"**回归实证：partition_test 32/0 → 29/3**"。**boot 侧若自建 partition 相关测试，必须复用该守卫宏约定**（写作 `defined(OM_OSAL_PORT) && (... == OSAL_PORT_NONE)`）。

**本决定的代价（记在明处）**：`is_erased` / `erase_unit_*` / `geom` 从"V1 应做"升为**首发消费者的承重项**——它们若延期，boot meta 直接受阻。反过来这也是收益：**接口会有一个真实消费者真的靠它活着**，正是 B3b 判据（"grep 有没有一处读它并返回错误码"）在项目内的自查。

## 1. 定位

### 1.1 一句话

> **在既有的分区语义层上，把「介质能力」交给消费者**——暴露**分区视图**（几何）、**窗口内擦除单位序列**、**已擦自检**，并定下**错误语义的约定**。目标是让消费者**以与具体器件无关的方式**读写裸 flash：换器件（片内 NOR → 外置 SPI NOR → 免擦块器件）时**消费者代码不动**。

**⚠️ 这是一次「补完」，不是一个新层**（见 §1.5）：地址窗口与边界校验 `partition v2` **已有**，几何 `FlashGeometry` **已有**——两者之间缺的只是**接缝**。**本文档初稿曾把它误称为"介质访问抽象"并画成独立一层，那是错误的**（与分区语义层职责重叠），已在 §1.5 更正。

**V1 只做可擦族**；跨族（随机器件 ER-3 / 块设备 ER-5）留给对应留口的触发条件。

### 1.2 它解决什么（三条痛点，均锚定现状）

| # | 痛点 | 现状证据 |
|---|---|---|
| 1 | **消费者拿不到"怎么写才对"的依据** | 几何（擦除单位、写单位、页边界、擦后值）决定提交协议能否成立，但它今天只存在于**器件层**：`FlashGeometry`（`pal_flash_dev.h:70-88`）与 `flash_geometry(dev)`。分区层的 `OmPartitionEntry` 只有 `(name, devName, offset, size)` —— **消费者要么假设是 NOR，要么依赖 drivers 内部头去 `flash_find` 绕路**。Zephyr 有**同款缺口**，代价有源码级证据：littlefs 适配层注释 `/* There's no flash_area API to implement this, so we have to make one here. */` |
| 2 | **边界与几何校验的归属不清** | 分区层 `open` 期已做"扇区友好"与越容量校验（`partition.c` 注册/open 段），器件层 `erase` 再做一次对齐断言——**能力都在，但没有一处对消费者可见**，于是每个消费者重复校验或干脆不校验 |
| 3 | **错误语义没有分层** | 消费者无法区分"稍后重试"（`OM_ERR_BUSY` / `OM_ERR_AGAIN` 已存在，`om_def.h:53/63`）与"这块介质不能用，换下一区"（业界 pstore/zone 用 `-ENOMSG` 表达）。缺的是**约定**，不是错误码本身 |

### 1.3 它明确**不**解决

| 不做 | 理由（业界实证） |
|---|---|
| **磨损与回收策略** | boot meta 是"留最新一份"、日志环是"留最新 N 条"，**语义不同**。调研 S1 结论原文："回收策略不要上移" |
| **数据组织**（环形 / KV / 文件） | S3 实证：连 MCUboot 都把记录布局**刻意保留三份**（`boot_status_internal_off` 三个文件各一份且已真实分叉） |
| **FTL / 块视图** | Linux 官方："nobody still managed to implement one for Linux"；`mtdblock` "in many cases … a very bad idea" |
| **跨族路由** | 随机器件走"命名窗口"、块设备走 disk 语义——`partition_table_design.md` §5 明确两者**都不并入**本抽象 |
| **异步性** | PAL 的"写必须让出 CPU"在成熟框架**无对应物**（它们是同步签名 + 可选 `sync` 回调）。异步是器件层实现细节，**不进本接缝**（一致于调研 §C.2/S1） |
| **掉电安全协议 / 校验** | 属"原子记录原语"，用户已明确**暂不做**。本接缝只提供它所需的**介质能力描述** |

**读法（三条）**：

1. **本次设计不是"新的一层管理逻辑"，而是把"地址窗口 + 几何 + 错误语义"合成消费者可依赖的面。** 它可能落在 partition 内（§4.4 落位 A）或作为薄模块（落位 B）——**无论落在哪，它填的是分区语义与消费面之间的那道缝**。
2. **管理层是空缺的，且这是刻意的**：用户裁决"暂不做原子记录原语"，所以记录格式 / 提交协议 / 轮转策略**由各消费者自己实现**（与业界一致——EasyFlash 的 ENV 与 LOG 不共享状态机）。本设计只提供它们所需的**介质能力描述**。
3. **横向只覆盖可擦族**：随机器件族（ER-3，"命名窗口"）与块设备族（ER-5，disk 语义）**各有自己的形态**，不并入本抽象；跨族选择在**板配置/构建期绑定**（`storage_landscape.md` §6.4）。

### 2.4 热路径改造：句柄缓存设备与几何（2026-09-18 用户决定）

**决定**：句柄改为**缓存设备指针与几何指针**（`om_partition_open` 期解析一次），**"信任开发者"**。

**现状代价**（实测代码）：每次 I/O 走 `partition_range()` → `partition_geom_check()`，内含
① `flash_find(e->devName)`（**链表遍历 + 名字比较**）；② `flash_geometry(dev)`；③ 容量越界；④ **`is_partition_sector_aligned(g, ...)`（非均一几何要遍历区域表）**。

**⚠️ 关键细节：只缓存"几何指针"不足以去掉名字解析**——写路径还需要 `FlashDev *` 才能调 `flash_read/write/erase`。所以要真正走进快路径，**必须同时缓存 `FlashDev *`**：

```c
typedef struct OmPartitionHandle {
    const OmPartitionRegistry *reg;   /* 所属注册表（不变） */
    uint32_t index;                   /* 操作期校验 index < reg->count（不变） */
    FlashDev *dev;                    /* open 期解析一次；设备为永驻对象（PAL：v0 无注销接口） */
    const FlashGeometry *geom;        /* open 期取一次；const，指向适配器的静态实例 */
} OmPartitionHandle;
```

**改造后每次 I/O 只剩**：越界（两次比较）+ 对齐（取模）——**纯常数级**。`is_partition_sector_aligned` 的全表遍历从热路径移除（open 期已做过）。

**两条必须一并落档的性质**：

1. **安全前提**：设备是**永驻对象**（`pal_flash_dev.h` 明文"设备为永驻对象（v0 无注销接口）"）⇒ 缓存指针**不会悬垂**。这是该改造成立的前提，**须写进注释**——将来若引入设备注销，此处即为破坏点。
2. **信任模型变化（记账）**：v2 原信任模型的要义是"**句柄无可伪造字段**，offset/size 恒从表取"（`partition.c:273-274` 注释）。缓存指针后，调用方**可以**篡改句柄字段——由"防伪造"降为"信任开发者"。**这是用户 2026-09-18 的明确取舍**（理由：热路径 + 几何可得性），设计稿须如实记录，避免后人误以为模型未变。

### 2.6 分区表的单一事实源：boot 与 app 怎么共用（B1 调研，2026-09-18）

**起因**：用户明确"**bootloader 计划复用分区表设计**"。我方现状是"**boot 与 app 各持一份编译期常量副本**"。B1 调研了六框架，结论是**建议放弃现状形态**。

**① 业界只有三类存放位置**：

| 形态 | 代表 | 一致性保证 |
|---|---|---|
| **构建期产物** | Zephyr DT / NCS Partition Manager | **单一求解器产单一配置**（结构性） |
| **介质内数据** | **ESP-IDF @0x8000**；NuttX（运行期解析 PTABLE/GPT/MBR） | **两侧读同一物理副本**（结构性） |
| 移植期常量（= **我方现状**） | MCUboot 各移植 `sysflash.h`；U-Boot `CONFIG_ENV_OFFSET` | **靠人** |

**② 关键事实**：**所有自动校验机制都只作用于"单侧"或"表自身"，没有任何一个是"两侧互校"的**——ESP-IDF 启动期 MD5（`esp_partition_table_verify()`，magic `0x50AA` / MD5 条目 `0xEBEB` / 终止 `0xFFFF`）只验表自身完整性；MCUboot Zephyr 的 `dt_nodelabel(... REQUIRED)` 只查自己那份；U-Boot `CONFIG_BOARD_SIZE_LIMIT` 只查尺寸。**靠人的那部分有原文**：MCUboot Cypress 移植 README 写 "make sure ... correspond to flash area size defined in **Applications' linker files**"；NCS 官方承认 `pm_to_dts.py` "is not guaranteed to produce correct output"。

**③ 失配的真实事故（最贴合我方风险的一条）**：U-Boot `saveenv` 写坏 U-Boot 本体——**pico-imx7d（2018）、mx6qsabrelite（2020）、mx6sabresd（2024），同一机制跨六年咬三个板子**。其中 2024 年 **`env: mmc` 的 GUID 越界**最像我们的场景：偏移由 GPT 推导覆盖了常量，`copy=1` 时算出**分区起点之前**的位置，**写坏相邻分区**；修法是加边界断言 `if ((1 + copy) * len > info.size) return -ENOSPC;` ⇒ **教训：凡从表推导出的偏移，必须带边界断言。**

**④ 布局指纹：六个框架里一个都没有**（"未找到"是明确结论，不是没查到）。替代路线只有两条——**消灭第二份**（ESP-IDF/NuttX：两侧读同一份）与**消灭分叉**（NCS：单一求解器，但最终仍放弃并迁回 devicetree）。**恰恰是"选了两份副本"的框架零指纹机制。**

**⇒ 对我方的建议（B1 原话的转述）**：

1. **现状（两份常量副本）建议放弃**——理由是**我方是通用 `{name, devName, offset, size}` 注册表，漂移面随条目数线性增长**（而 MCUboot 只有 4–5 个固定角色，所以它扛得住）。
2. **推荐"介质内数据"形态**：编译期常量数组**降级为编写形式**（单一源），构建期**序列化进 meta 区**。理由：boot 侧 meta 区要求 **≥3 个独立擦除单位**——**正好够 2 副本 + 第 3 份（或日志）+ CRC/version**。且**相对 ESP-IDF 有实质改进**：ESP-IDF 的 MD5 **只防坏不防丢**（无冗余副本），我方 3 个擦除单位**两者兼防**。
3. **指纹该做但不该指望**（无惯例可抄）：建议 **bootloader 侧只写不判**（记录"我依据的指纹"），**app 侧比对后拒绝用自己那份副本寻址/写 flash**，改为降级去重新解析 meta。指纹取**规范化序列的 hash**——**不要** hash C 结构体的内存布局（padding/字节序/`devName` 是指针还是索引都会自造漂移）。
4. **唯一必须保留的编译期常量 = 引导链锚点**（bootloader 分区 / meta 区 / 表在 meta 中的偏移），应显式隔离为"**不可漂移**"的小集合。
5. **另抄一条**：**构建期断言"镜像 ≤ 分区 size − 余量"**——U-Boot 三起事故证明没有它不行。

**⚠️ 未证实项（勿当事实引用）**：ESP-IDF bootloader 校验失败后的兜底行为；MCUboot "与下载脚本一致"**未找到**一手来源（该措辞只在具体移植 README 且只提链接脚本）；Zephyr 官方是否显式声明两侧 DT 须逐字段一致（**未找到**）；ESP-IDF "single source of truth" 逐字表述（**未找到**）。

**⚠️ 与 boot 侧的接口**：形态 2 意味着**分区表要住进 meta 区**——那是 boot 侧的地盘（K-30/K-36 已定 meta = 独立区 + 32B entry + ≥3 份 + 擦除归引导侧）。**采纳前必须与 boot 侧对齐**，本设计不单方面决定。

### 2.5 分区层的价值论证（为什么工作落在这一层，而非并入器件层）

> 起因：质疑"器件层已有读写擦 + 几何，分区层是不是多余的薄转发"。**两条独立调研（P1/P2）结论一致**。

**① "转发那部分确实薄"——这话有出处**：Zephyr 官方文档自认 `flash_area_read/write/erase` 是 "basically wrappers around the flash API with additional offset and size checks"。

**② 但没有任何成熟项目删掉过分区概念**：Zephyr / ESP-IDF / Linux MTD / RT-Thread FAL / NuttX **五家全保留**，且**越界预校验全部在每次 I/O 上做**。反向演进的两例都**不构成反例**——MCUboot v1.2.0 删的是**自己那份重复的 `flash_map`**（改用平台的），NCS 在 DT ↔ Partition Manager 之间来回迁，**删的都是重复实现，不是分区层**。

**③ 器件层在原理上表达不了的一条**：MCUboot 给分区的定义是**擦写隔离不变式**——"An area can be fully erased without affecting any other areas"。**这是分区语义，不是器件物理语义** ⇒ 器件层表达不了。**与 §6.6 设计不倒挂原则完全同向**（器件层的每个决策必须能由器件物理语义 + 业界收敛独立解释，不引用上层消费者；而"谁用哪块地"本就是上层需求）。

**④ "薄转发"的批评有一半是对的，但归位错了**：P2 的结论原话——**被质疑的应是"谁来持有这张表"，不是"要不要分区层"**。12 种替代机制（闭包/devicetree/盘上表/编译期常量+断言/链接脚本/固定偏移/运行时探测/器件自描述/物理分离/构建期分配器…）**没有一种能同时满足"跨镜像一致 + 运行时可查 + 零额外事实源"**；能"事前"拦住的只有链接器与构建期分配器。

**⑤ "没有分区层会怎样"——三个血泪案例**（P1）：U-Boot 硬编码 `CONFIG_ENV_OFFSET` 与镜像**重叠** → `saveenv` 挂死/不可启动（修法是加构建期尺寸限制）；2024 年 env/mmc 从分区尾**倒推**偏移小于分区起点 → **随机破坏前一个分区**；Zephyr #117802 DFU 误选 `slot0`（实际跑 `slot0_ns`）→ **擦掉正在运行的槽位**。
**反面也有一条**：Linux 2015 年**主动删除**了重叠检查以支持 rootfs split ⇒ **"隔离"是策略，不是不变量**（我们选择保留它）。

**⑥ 一处已收回的"更严"主张（2026-09-19 更正，勿再引用旧说法）**

**原表述**：Zephyr 与 ESP-IDF **都缓存设备指针**；我们**刻意每次 I/O 按名重解析**（`partition.c:273-274` 注释写明理由：句柄若缓存 `FlashDev*`，器件指针即成可伪造/可悬垂的字段，破坏"offset/size 恒从表取"的信任模型）⇒ 结论"**比业界更严**"。代价 = `flash_find` + 几何/扇区友好校验，microsecond 级（相对 256 B 编程 ~1 ms 是 <1%）。

**⚠️ 该结论已被 §2.4 推翻**（决定改为缓存设备与几何指针，"信任开发者"）——**"比业界更严"不再成立**，本设计在这一项上与 Zephyr/ESP-IDF **同形**。

**更正后的诚实表述**：这是一次**显式交换**——用**设备指针的不可伪造 / 不可悬垂性**，换掉**每 I/O 的名字解析开销**。

| | §2.4 之后 |
|---|---|
| **仍成立** | **"offset/size 恒从表取"**——每次 I/O 依旧 `partition_handle_valid` + `partition_entry_at(reg, index)`，offset/size 读的是表，不是句柄字段 |
| **已让出** | `dev` 指针成为**可伪造字段**（句柄被写坏即可指向任意设备）；悬垂风险由"**设备永驻**"消解（PAL v0 **无注销接口**，故指针不会失效） |

**⇒ 使用约束（必须进 ADR）**：**若将来 PAL 引入设备注销/重注册，"设备永驻"前提失效，本交换必须重估**。

**⇒ 结论**：

| 判断 | 结果 |
|---|---|
| 分区层是否多余 | **不多余**——它守的是"命名/所有权 ABI + 每 I/O 校验 + 隔离"，且没有人删掉过 |
| 能否并入器件层 | **不能**——违反 §6.6 不倒挂原则（"谁用哪块地"不是器件物理语义） |
| 它的正确定位 | **"命名与所有权（ABI）层"**（P1 建议），转发只是表象 |
| 字段选得对不对 | **对**——`{name, devName, offset, size}` 与 Zephyr/ESP-IDF/MCUboot **同构**（P2） |

**P2 建议我们补的三个缺口**（与"性质乙"部分重合，值得纳入考量）：① **枚举能力**（已在本设计 §4.2 的擦除单位枚举里）② **运行期可自建分区**（Zephyr 明文允许，我们只在编译期有注册表）③ **分区上的能力声明**（对标 ESP-IDF 的 `readonly` / `encrypted` / `erase_size`）。

**bootloader 侧的两条建议**（P2，转述）：槽位 ID 做**编译期常量 + `_Static_assert` 判重**（MCUboot 有 `DT_SAME_NODE` 编译期判重先例）；考虑给分区表算**布局指纹**供 boot/app 启动比对——**业界无人做，属差异化机会**（该线注明"建议非事实"）。

### 4.5 窗口内擦除单位：形态与依据（B2 调研，2026-09-18）

**业界只有四种暴露形态，其中三种在器件层，只有一种在分区层**：

| 形态 | 代表 | 在窗口内？ |
|---|---|---|
| **数组 + in/out count** | **Zephyr `flash_area_sectors(fa, &count, sectors[])`** | ✅ **唯一在分区层的** |
| **count/at 索引** | Linux `MEMGETREGIONCOUNT` + `MEMGETREGIONINFO(index)` | 器件层 |
| 点查询 | Zephyr `flash_get_page_info_by_offs(dev, offs, &info)` | ❌ 不带窗口 |
| 迭代器 | Zephyr `flash_page_foreach(dev, cb, data)` | ❌ 不带窗口 |

⇒ **没有任何一家用迭代器暴露"窗口内序列"**——印证 §4.2 的 `count/at` 选择。

**非均一擦除单位：只有两家支持，且都靠"等尺寸段的数组"**：Zephyr `flash_pages_layout{pages_count, pages_size}[]`、Linux `mtd_erase_region_info{offset, erasesize, numblocks}[]`——**与我方 `sectorRegions[]` 同构**。其余全是"单值派"：**假设均一**（littlefs 的 `erase(c, block)` **没有长度参数**、地址靠 `block*block_size` 推——**结构上不可能支持非均一**；ESP-IDF 硬编码 `SPI_FLASH_SEC_SIZE`）或**取最大**（Zephyr 的 littlefs 适配层、FAL 的 STM32F2 样例 `.blk_size=128K`）→ 容量浪费 + 逻辑块跨物理扇区。

**"窗口 ∩ 区域表"的裁剪：有先例，但没有一个把两件事同时做对**：
- **真裁剪**：Linux `mtdpart.c allocate_partition()` 扫窗口内区域段**取 max**，再对齐门禁——**起点/终点不按 max 对齐则清除 `MTD_WRITEABLE` 强制只读**；源码留 `FIXME` 自认应按更小单位；
- **保留多尺寸**：Zephyr `flash_area_sectors()` **只按页起点归属，不裁剪不报错**。

**未对齐时的四种策略**：拒绝（ESP-IDF `ESP_ERR_INVALID_ARG` / NuttX `DEBUGASSERT`）· 外扩（Linux `mtd_align_erase_req()`、FAL 循环）· 按起点归属（Zephyr）。

**⇒ 对本设计的确定项**：

| 项 | 结论 | 依据 |
|---|---|---|
| **API 形态** | **`count/at` 为主 + 点查询为辅 + 迭代器降为可选旁路** | FCB 是最近范式：持 `f_sectors[]` 数组、`f_sectors[i]` 取第 i 块、`fcb_getnext_sector()` 回绕、擦除用 `flatten(fs_off, fs_size)`。**"擦除单位由数组元素携带，而非分区级标量"——这才是非均一能成立的根本** |
| **偏移基准** | **一律"分区内相对"，并写死文档** | 反面教材：Zephyr `fs_off` 的**头文件注释与实现矛盾**（注释说器件起点，实现减了 `fa_off`）——我们已在 §4.2 定"分区内偏移"，须在注释里写死，不留歧义 |
| **未对齐策略** | **配置期 REJECT**（不做运行时分支），**绝不默认外扩** | 分区是静态配置，一次校验后运行期零分支；**对环形日志"外扩"会擦掉相邻记录** |
| **规模** | **不物化数组**——按需走步枚举 ⇒ **上限概念不存在，更无 ENOMEM 路径**（2026-09-19 落码后强于原"静态上限 32"） | B2 实测计数 + 落码 |
| **建议补充两个查询** | **`is_uniform()` / `max_erase_unit()`** | 让"取最大"成为**显式决策**，而非静默行为（Zephyr 的 littlefs 适配层正是静默取最大） |

**★ 意外收获（对日志环直接可用）**：**Zephyr `stream_flash.c` 是日志环的最佳模板**——它用 `flash_get_page_info_by_offs()` 拿**真实的 `page.size`** 来前进（`ctx->erased_up_to += page.size`），**在非均一器件上天生安全**。我们的日志环应照此形态设计，而不是假设固定块大小。

**另**：FAL 的 STM32F2 移植样例里那份扇区表**正是我方 F427 的几何**（`16K×4 + 64K×1 + 128K×7`），且它示范了"**点查询不物化数组**"的擦除范式（`get_sector(addr)` + `get_sector_size(sector)` + `while` 累加）。

### 1.4 为什么它不是"块设备"（术语澄清，避免将来被误改）

| | 块设备族 | 本抽象 |
|---|---|---|
| 擦除 | **被隐藏**（内部 FTL 负责） | **显式暴露**（`eraseUnit` / `erasedValue`） |
| 写 | 覆盖写 | **写前必须已擦**（program 语义） |
| 位语义 | 无约束 | **单向写（1→0）** |
| 扇区 | **固定**（512 B / 4 KB） | 可变、且**同一器件内可非均一**（多段不同扇区尺寸） |
| 谁付 FTL 的账 | 受管封装（SD/eMMC 硬件）或主机软件 FTL | **没有 FTL** |

**两者的设计意图相反**：块设备让擦除不可见，本抽象让擦除可见。
**命名纪律**：叫「**介质访问抽象**」或「裸可擦介质接口」，**不要叫"块设备层"**——否则后来的人会往里塞 FTL，或按块设备假设写代码。
（用词提醒：ESP-IDF 那个新组件确实叫 **BDL `esp_blockdev`**，而它带 `erase_size`/`default_val_after_erase`——**业界用词是松的，要看语义不看名字**。）

## 2. 现状：**能力已在，接缝未成**

这是本设计最重要的判断——**不是"补一个新能力"，而是"把已有能力合成一个稳定的、面向消费者的接缝"**。

| 已有 | 位置 | 内容 |
|---|---|---|
| **几何** | `pal_flash_dev.h:70-88` `FlashGeometry` | `capacity` / `erasedValue` / `writeUnit` / `pageSize` / `sectorSize` / `sectorCount` / **`sectorRegions`（非均一区域表）**；经 `FLASH_CMD_GET_GEOMETRY (0x10U)` 与 `flash_geometry(dev)` 取得 |
| **地址窗口** | `partition.h:42-69` | `OmPartitionEntry{name, devName, offset, size}` + `OmPartitionHandle{reg, index}` |
| **边界检查** | `partition.c`（open 期扇区友好 + 越容量）、`pal_flash_dev.h`（erase 对齐断言） | 两级防线（差距分析记为优势项 **S-02**） |
| **错误码** | `om_def.h:47-67` | 18 个通用码，且**不设兜底码**（"强制开发者明确错误归因"）；支持 `0x001-0x0FF` 模块别名 |

**对比业界**：我们的 `FlashGeometry` **比 ESP-IDF 新版 BDL 的四项更全**（多了非均一 `sectorRegions` 与 `pageSize`）。**所以差距不在能力，在暴露。**

**缺的三件事**：
1. **消费者拿不到几何**（唯一入口是 drivers 内部头 + `flash_find`）；
2. **分区内的擦除单位序列拿不到**——`open` 期明明校验过"扇区友好"，却没有 API 枚举"这个分区里有哪些扇区/擦除单位"。**消费者要做环形/布局，恰恰需要这个**；
3. **错误语义没有成文约定**（"稍后重试" vs "换下一区" vs "格式不兼容"）。

### 3.2 V1 追加两项能力（2026-09-18 用户决定：需要；B3 调研已回，2026-09-19 定案）

#### ① 运行期可自建分区 → **形态 A：调用方自填表**，不新增注册 API

**五家框架全部支持运行期追加，但形态分四类**（B3a）：

| 框架 | 形态 | 持久化？ | 重叠仲裁 | 关键事实 |
|---|---|---|---|---|
| **Zephyr** | **自建对象**（无注册 API） | ✗ | 无 | 官方原话是 `Users may also create flash_area objects at runtime`——**create objects**，不是 register partitions；运行期对象**不进 flash map**，`flash_area_open()` 看不到它 |
| **ESP-IDF** | `esp_partition_register_external()` | ✗ | **✓ 唯一有仲裁的** | `bootloader_util_regions_overlap()` 重叠即 `ESP_ERR_INVALID_ARG`；`user_registered` 标志使**表内分区永久不可注销**（冻结语义） |
| **Linux MTD** | 内核 `mtd_add_partition()` / `ioctl(BLKPG)` / `mtdparts=` | ✗ | **零重叠检查** | `cmdlinepart.c` 官方明文 `may even overlap` |
| **U-Boot** | `mtdparts add` → `env_set` → `saveenv` | **✓ 唯一** | 无 | 与 `CONFIG_ENV_OFFSET` 是**鸡生蛋关系**（要读 env 得先知道 env 在哪）；官方注释：`once mtdparts is saved environment, drop use_defaults flag` ⇒ **编译期默认值此后永久失效** |
| **NuttX** | 公开的只有 `parse_block_partition()` / `parse_mtd_partition()` + 回调 | ✗ | 无 | `register_partition()` 是 `fs_partition.c` 里的 **static** 内部函数，不对外 |

**核心结论：没有任何框架提供"运行期注册 API + 持久化 + 单一事实源"三合一。** 三种化解路线是**隔离**（Zephyr，运行期对象与静态表互不可见）· **仲裁 + 冻结**（ESP-IDF）· **让表本身可变且唯一**（U-Boot，代价是编译期默认值失效）。

**我们的答案：形态 A，且不需要新 API。** `OmPartitionRegistry{table, count}` 的**表指针已可指向调用方 RAM**（`partition.h` 明文）⇒ "运行期构造一张表再 open"**今天就能做**。Zephyr 的新发现 `CONFIG_FLASH_MAP_CUSTOM` 印证了这个形态是对的——它的表本体就是
`extern const struct flash_area *flash_map; extern const int flash_map_entries;`，**构建期整份替换，与我们的 `{table, count}` 同构**。

**必须写进接口文档的五条边界**（B3a 从 8 例翻车中归纳，**没有一例是"分区重叠"直接导致崩溃**——真凶全是运行期引入的新状态空间）：

1. **表内自检防溢出**：用 `len <= total - off` 而非 `off + len <= total`（Zephyr issue #89349 整数溢出，**自 v1.11.0 潜伏多年**）
2. **不跨表仲裁**：框架不合并多个 registry；"按名查找"的语义边界就是单表
3. **表生命周期归调用方**，框架**不缓存表指针**（与 §2.4 缓存设备/几何指针不矛盾——那两项是新解析出的框架内副本，表是调用方资产）
4. 表**为空/未初始化**时 open 必须返回错误而非 panic（NuttX TXTABLE 表缺失 → 内核 panic 是反面教材）
5. 容量不足时**返回错误**，绝不静默截断（U-Boot 超限逐字 `resetting to null`，**清空整表**）

**"运行期追加"要先分辨三种诉求**（用户原话含混，三者代价差别极大）：

| 诉求 | V1 态度 |
|---|---|
| **(a) 操作表外区间**（临时访问一段未登记地址） | ✅ **V1 就该支持**，零风险——调用方现场构造一条记录即可 |
| **(b) 现场划分，且重启后还在** | 🔜 **明确记为 T2**；**V1 必须在文档里写清"重启后不存在"** |
| **(c) 把外部介质纳入统一寻址** | ✅ 用**调用方构造表**覆盖即可，**不需要框架内集合**（与 §3.1 的族分立一致） |

#### ② 分区上的能力声明 → **加字段，不加平行表**；且 `allow_erase` 必须重新设计

**业界实际声明的能力清单**（B3b）：

| 框架 | 能力 | 形态 |
|---|---|---|
| **Linux MTD** | `MTD_WRITEABLE` / `MTD_BIT_WRITEABLE` / `MTD_NO_ERASE` / `MTD_POWERUP_LOCK` / `MTD_SLC_ON_MLC_EMULATION` + `MTD_CAP_*` 组合宏 | 位域，最丰富 |
| **ESP-IDF BDL** | `read_only` / `encrypted` / `erase_before_write` / `and_type_write` / `default_val_after_erase` + **`reserved: 27`** | 结构体，**最结构化** |
| **ESP-IDF 分区表** | **只有一列 `Flags`**，仅 `encrypted` / `readonly` | CSV |
| **Zephyr** | 只有 `label` / `reg` / `read-only` | DTS binding |
| **U-Boot** | 只有 `ro` | env 字符串 |

**判据（B3b 给的，可直接当 review checklist）：grep 有没有一处读它并返回错误码。** 没有强制点的声明 = 装饰。

**"声明了没人读"实证 5 例**，成因分四类：

| 案例 | 成因 |
|---|---|
| **Zephyr `read-only`**：binding 有、`fixed-partitions.h` 无宏、`struct flash_area` 无字段、`flash_area_write/erase` **不检查**；issue #30587 / #43052 **至今 open**，PR #36979 曾实现又**撤出** | 声明在错误的分层，消费者层无法强制的语义被下放了 |
| **U-Boot**：同一个 `ro` **两套解析器两个常量**（`cmd/mtdparts.c` 用 `1`，`drivers/mtd/mtdpart.c` 用 `0x400`），文档写 "not used" **已过时** | 同一概念重复定义 → 必然漂移 |
| **U-Boot `cmd/mtdparts.c:1159`** 的 `&&` 笔误**靠常量恰好 ==1 侥幸正确** | 同上 |
| **Linux `mtd_part.flags`** 只写不读（`mtdpart.c` 拿 `mtd_flags` 当入参，但**不存进 part**） | 声明与强制点不在同一层 |

**强制性放哪：必须在框架层。** Linux 把检查放在 `mtd_erase` / `mtd_writev`（返 `-EROFS`）和 `mtdchar` open（返 `-EACCES`），**6 条访问路径全拦住**；只放消费者层会漏。

**⚠️ 决定性发现：`allow_erase` 是主体相对的（subject-relative）——一张 boot/app 共用的编译期常量表在结构上装不下它。**

Zephyr issue #43052 的原文论证：**app-partition 对 bootloader 可写、对 app 只读**——同一条分区记录，能力取决于**谁在问**。这与 §3.3 的 T1（单一常量表 + 两侧 include）直接冲突：表里没有"调用方是谁"这一维。

**⇒ 由此定案（B3b 建议 + 与 T1 相容的唯一形态）：**

1. **`allow_erase` 不做成表里的布尔字段**，改为 **策略枚举** `ERASE_ANY` / `ERASE_BOOT_ONLY` / `ERASE_NEVER`；
2. **每工程定义一个编译期自身身份常量**（`OM_PARTITION_SELF = OM_ROLE_BOOT` / `OM_ROLE_APP`）；
3. **强制点放在框架的 `part_erase()` 内**：`(策略, 自身身份)` **取交集**才放行——即 NVS "分区声明 × handle 模式取交集"的成熟形态；
4. 这样**同一张表对 boot 与 app 都成立**，T1 单一源不被破坏。

**其余四项介质能力的收法**（2026-09-19 用户决定："不复杂就 V1 全上"；核实后结论：**三项是投影，一项绝不能加标量**）

**⚠️ 首要结论：这四项没有一项该进 `OmPartitionEntry`（boot/app 共享常量表）。** 它们是**介质物理事实**——驱动手上有器件手册，该住在 `FlashGeometry`，由分区视图**投影**出去。真正要进共享表的**只有策略/权限**（`allow_erase`）。

| 项 | 现状（源码核实） | V1 结论 | 工作量 |
|---|---|---|---|
| **`erasedValue`** | **已在** `FlashGeometry`（`pal_flash_dev.h:78`，注释逐字"器件物理特性"） | ✅ **上**——投影 | 投影代码（§4.1 草案已有字段，`partition.h` 当前**零实现**） |
| **`writeAlign`** | **就是 `writeUnit`**（`pal_flash_dev.h:80` 注释"写对齐粒度"）；**器件层已强制**：`addr % writeUnit != 0 \|\| len % writeUnit != 0` → `OM_ERR_INVALID_ARG`（`hal_flash.c:492`、`:547` 两处） | ✅ **上**——投影 | 同上，**零新逻辑** |
| **`eraseAlign`** | — | ⛔ **不加标量** | **0**（但必须写清"为什么"，见下） |
| **`eraseBeforeWrite`** | **真的缺**：`FlashOps.write` 契约写"目标已擦"（`pal_flash_dev.h:107`），但器件层**不验证**（只查空指针 + `writeUnit` 对齐） | ✅ **上**——加进 `FlashGeometry` + 投影 | **1 行派生** |

**⛔ 为什么 `eraseAlign` 不能是标量（此条须显著，否则将来一定有人加回来）**

非均一几何下"对齐"**不是模运算**。在一个含多种扇区尺寸的器件上，**按较小尺寸对齐的地址若落在更大扇区内部，根本不是可擦边界**——消费者若按 `eraseAlign = 最小尺寸` 推算"这个地址可以起擦"，**会擦掉整个大扇区**。

器件层正是为此**没有**用模运算：`flash_erase_validate`（`hal_flash.c:93-112`）判定的是**区间两端都是扇区边界**，注释逐字"跨大小不同的区域也成立"。**⇒ `eraseAlign` 的正确形态已经在 V1 里**：`om_partition_erase_unit_at/covering` + `is_uniform()` / `max_erase_unit()`。一个标量字段会被误当成"可擦性判据"，**比不加更坏**。

**⚠️ 更正（2026-09-20 用户指出）：`eraseBeforeWrite` 不能用 `bool`**

原设计写 `bool eraseBeforeWrite`。**这违反了本设计 §3.2② 自己定的规则**——"把最保守值放枚举第 0 位（漏填 = 最保守）"：

| 形态 | 零值/漏填时的语义 | 落在哪一侧 |
|---|---|---|
| `bool eraseBeforeWrite` | `false` = "不需要写前擦除" | ⛔ **最危险的一侧**——消费者跳过擦除直接写未擦区 = 静默坏数据 |
| 否定式位 `noEraseNeeded` | `0` = "须擦" | ✅ 保守一侧（多做一次擦除，浪费但安全） |

**业界形态（B3b 一手证据）**：
- **ESP-IDF BDL**（最结构化的先例）用**位域 + `reserved: 27`**：`uint32_t erase_before_write: 1;`——**不是裸 bool**；`reserved` 的作用是"新增能力位不改结构体大小、不破 ABI"
- **Linux MTD** 用 **`MTD_NO_ERASE`——否定式 flag**（置位声明例外，不置位 = 保守默认）
- （注：ESP-IDF 自己的分区表 `esp_partition_info_t` 确实用裸 `bool`——所以这是"最优形态 vs 可用形态"之别，我们取最优）

**⇒ 定案**：`OmPartitionGeom.caps` 为 `OmPartitionCapFlags`（1 位否定式 + 31 位 `reserved`），配 `om_partition_needs_erase()` 解包读法。原 `bool eraseBeforeWrite` **删除**。

**`eraseBeforeWrite` 怎么加（本项唯一的新代码，且是派生而非新事实）**

- 加进 **`FlashGeometry`**（驱动填）——**只有驱动知道**这条规则；
- 值**由擦除单位是否存在派生**：有 ⇒ `true`；**ER-1 免擦块器件 `eraseUnit == 0` ⇒ `false`**（与 §3 范围表已定条目**同源，不产生第二处定义**，符合 B3b"避免重复定义 → 必然漂移"的教训）；
- **投影进 `OmPartitionGeom`**，消费者看到具名字段；
- ⚠️ **派生成立的前提是当前 `FlashOps.write` 契约**（"目标已擦"，即驱动不做 RMW）。**若将来允许驱动内部 RMW，此派生失效，必须改为驱动显式声明位。**
- **不做验证**：器件层要验证就得读回整段 = **I/O 翻倍**。取**声明 + `om_partition_is_erased`（已在 V1 接口）供消费者自检**——这是 B3b"有强制点才加"判据下最省的形态。

**⇒ 由此得到"能力声明该放哪"的总规则（本节真正的产出）**

| 类别 | 例子 | 谁最先知道 | 放哪 | 主体相对 |
|---|---|---|---|---|
| **介质物理事实** | `erasedValue` / `writeUnit` / `eraseBeforeWrite` | **驱动** | **`FlashGeometry`** ⇒ 投影进 `OmPartitionGeom` | 否 |
| **几何形状** | 擦除单位序列 / `is_uniform` | 驱动（`sectorRegions`） | 同上，**且必须数组而非标量** | 否 |
| **策略 / 权限** | `allow_erase` | **产品与 boot/app 的约定** | **`OmPartitionEntry`（共享表）**，策略枚举 | **是** |

**这条规则顺手解掉了本节的 ABI 纠结**：先前记的"加字段 = boot/app 两侧同时改"——**只对 `allow_erase` 成立**。三项物理事实走 `OmPartitionGeom`（**运行期投影视图，不是 ABI 共享表**），**与 boot/app 的编译期耦合无关**。

**同一条原则下的隐患已清除（2026-09-19，顺手做掉）**：`writeUnit` 对齐规则原在 `hal_flash.c` **写了两遍**（async 路径、sync 路径，注释自承"与 async 同一语义"）——**"同一规则两处定义"正是 B3b 里 U-Boot `ro` 两个常量（`1` vs `0x400`）漂移的同型风险**。已提取为单一 `flash_write_validate()`，与既有 `flash_erase_validate()` 成对：

```c
/* 写单位全局均一 → 模运算；擦除单位可能非均一 → 只能判"两端是否扇区边界"。
 * 两者刻意不同型：模运算在非均一下会把扇区内部的 16K 对齐地址误判为可擦起点 */
static OmRet flash_write_validate(const FlashGeometry *g, uint32_t addr, const void *data,
                                  size_t len);
```

**⇒ 这正是 `eraseAlign` 不能是标量的代码级证据**：同一个文件里，写制用模运算、擦制用边界判定，**两张校验函数的形态不同，就是因为在非均一几何下模运算对擦除不成立**。

**策略字段的形态定案（`allow_erase` 用）：**

- **加字段，不加平行表**——平行表引入的 join 会漂移，必然退化成 Zephyr 式空声明；
- 用 **C11 指定初始化器**，**最保守值放枚举第 0 位**（漏填 = 最保守）；
- 预留 **`reserved` 位域**（学 ESP-IDF BDL 的 `reserved: 27`）；**未知位告警而非崩溃**，但需约定"新增能力位时 boot/app 必须同编译"。
- **`encrypted` 暂不引入**：无实际密钥路径时它就是个装饰（B3b 判据）。

### 3.3 分区表的形态：T1 定案，T2 演进（2026-09-19 用户决定）

| | 形态 | 写入者 | app 是否嵌副本 | 状态 |
|---|---|---|---|---|
| **T1** | **编译期常量表**：**一个头文件被 two 工程 include**（编写单一源） | **无**（它就是常量） | 是 | ✅ **V1 采用** |
| **T2** | **持久化表**：bootloader 播种进 meta 区，boot 与 app 都读介质那份 | 产线烧写工具 / bootloader（首次上电 · 布局变更时）；**app 永远无写权限** | **否** | 🔜 演进 |

**T2 的诱人之处（记账留档）**：app 不携带自己的副本 ⇒ **"旧 boot + 新 app"的版本错配在结构上不成立**（双方读同一份物理数据）。ESP-IDF 正是靠这一点绕开整个漂移问题；而**它的表只防坏不防丢**（MD5 无冗余），**若我们放进 ≥3 擦除单位的 meta 区，可两者兼防**。
**T2 的成本**：① 要动 boot 侧 meta 区划分（32B entry 与几百字节的布局表如何共享 ≥3 个擦除单位）；② 需要"表无效时 boot 怎么办"的兜底路径。**且必须与 boot 侧对齐——本设计不单方面决定。**

**布局防漂移机制 = 演进项，且已由 boot 侧认领**（2026-09-19 用户确认）：**boot 侧已计划把布局指纹写进 meta**，同为演进项。⇒ **本设计不再重复规划、也不做对齐**（§5.3）。背景留档：业界基本"交给程序员保证"（Zephyr/NCS 明说责任在人；U-Boot 三次事故为证），**唯一的结构性解法是 T2**，B1 建议的"指纹"业界无人实现。

### 3.1 EEPROM / SD 要不要接入分区层？（2026-09-18 提问）

**答：不接入分区层；但"命名窗口"这个概念保留，各自成形。**

**① 分区层守的不变式在那些介质上不成立或另有归属**（P1/P2 的核心发现）：

| 介质 | 分区层的"擦写隔离不变式" | 结果 |
|---|---|---|
| 可擦 NOR | 成立——"An area can be fully erased without affecting any other areas" | 分区表正是表达它的形态 |
| **EEPROM / FRAM** | **无擦除** ⇒ 退化为"地址不重叠"，**扇区对齐校验是空壳** | `partition_table_design.md` §5 原文即"无扇区/擦除语义的分区表是空壳" |
| **SD / eMMC** | 受管封装，隔离由 **GPT/MBR + FTL** 表达，且**表在介质内** | §5："由 FS/disk 层语义承担（ER-5），不混入裸片存储抽象" |

**② 业界同样是族分立**（P2 实证）：Linux 对 EEPROM 类用 **nvmem cells**（**不是** MTD partitions）、对块设备用 **GPT + 块层**、对裸 flash 才用 MTD partitions；littlefs 干脆**把区域概念下推成块设备回调**——"partition" 一词在其 `lfs.h` / SPEC / DESIGN / README 中出现 **0 次**。

**③ 消费者要的"统一"不在这层**（`storage_landscape.md` §6.4）：**消费形态窄接口 + 族内适配 + 构建期绑定**。日志若要同时支持 NOR 与 SD，做法是**两个后端实现同一个窄接口**（ArduPilot 的文件后端与块后端共用一个 `AP_Logger_Backend` 基类），**不是让两种介质共用一个分区层**。

**④ 一条诚实的保留**：**"命名窗口"与"分区"在数据结构上高度相似**——都是 `name → {dev, offset, size}`，差别只在**校验内容**（扇区/擦除单位 vs 无）。所以 ER-3 落地时，"命名窗口"很可能是**分区模块的族特化**（同一注册表结构、跳过可擦族专属校验），而不必从零再写一套。**此判断留到 ER-3 触发时再定，现在不预设。**

## 4. 接口草案

### 4.1 消费者视图的能力描述

**不直接把 `FlashGeometry` 甩给消费者**（它含器件级字段与**整器件**区域表）；给出**分区裁剪后的视图**：

```c
/* —— 分区能力标志：**位域 + reserved，零值 = 最保守** ——
 * 形态学 ESP-IDF BDL（reserved:27）；位取**否定式**（学 Linux MTD 的 MTD_NO_ERASE）：
 * 置位 = 声明例外，未置位（含零初始化/漏填）= 保守默认。
 * ⚠️ 不用 bool —— bool 的零值 false 在此语义下恰是最危险的一侧（见 §3.2②） */
typedef struct {
    uint32_t noEraseNeeded : 1;  /* 0 = 写前须擦（保守）；1 = 免擦器件 */
    uint32_t reserved : 31;
} OmPartitionCapFlags;

/* —— 分区视图：只含"与地址无关"的器件能力 + 分区自己的容量 ——
 * 全部由 FlashGeometry 投影而来（§3.2②：物理事实不写进分区表） */
typedef struct {
    uint32_t capacity;        /* **分区**字节数（不是器件容量） */
    uint16_t writeUnit;       /* 最小写单位（= 写对齐粒度，字节） */
    uint16_t pageSize;        /* 最优批量写页；0 = 无偏好 */
    uint8_t  erasedValue;     /* 擦后值；免擦介质由**器件**声明（不硬编码 0xFF） */
    OmPartitionCapFlags caps; /* 能力标志（未置位 = 保守默认） */
} OmPartitionGeom;

/* —— 窗口内的擦除单位（派生：分区窗口 ∩ 器件区域表）—— */
typedef struct {
    uint32_t offset;   /* **分区内**偏移——与 partition 其余 API 的偏移语义一致 */
    uint32_t size;     /* 该擦除单位的大小（**非均一几何下会变**） */
} OmPartitionEraseUnit;
```

**⚠️ 注意：分区视图里没有 `eraseUnit` 标量**——这是 B2 调研纠正的一处实质错误。**器件的擦除单位可以是非均一的**（同一器件内多段不同扇区尺寸），"一个擦除单位的大小"**根本不存在**。B2 的原话：

> **擦除单位由数组元素携带，而非分区级标量——这才是非均一能成立的根本。**

（反面教材：Zephyr 的 littlefs 适配层与 FAL 的 STM32F2 样例都**静默取最大**，换来容量浪费与逻辑块跨物理扇区。）

**`erasedValue` 必须支持 `0x00`**（ESP-IDF BDL 显式支持两种，见调研 S1）。

### 4.2 操作面（含**擦除归属的两种模式**）

**核心判断**：两种消费者对擦除的**权限完全不同**，但需要的**原语相同**——所以差异不该落在"两套 API"，而该落在**句柄属性 + 契约**上。

| 模式 | 消费者 | 谁擦 / 何时 | 必须维持的不变式 |
|---|---|---|---|
| **M：引导期擦除** | boot meta（K-36 已定） | **引导侧**（引导期擦"非最新份"；此期无应用并发） | **池中始终至少一份已擦副本** + **永不擦最新有效份** |
| **R：运行期擦除** | 持久化日志环 | **消费者自己**（环形轮转 / erase-ahead） | **下一个要写的块已擦** |

**接口**（操作面对两种模式统一）：

**⚠️ 数据面不新增任何 API**——`om_partition_read` / `write` / `erase` / `erase_range` **已经存在**（分区句柄 + 分区内偏移）。本次**只新增"能力与几何"的查询面**：

```c
/* —— 分区视图（§4.1）—— */
const OmPartitionGeom *om_partition_geom(const OmPartitionHandle *h);

/* —— 窗口内擦除单位：count/at 为主（B2 印证：分区层唯一的先例形态）—— */
uint32_t om_partition_erase_unit_count(const OmPartitionHandle *h);

                                    OmPartitionEraseUnit *out);

/* —— 点查询：给"已知偏移，问它在哪个擦除单位"（B2 建议的辅助形态）—— */
OmRet    om_partition_erase_unit_covering(const OmPartitionHandle *h, uint32_t off,
                                          OmPartitionEraseUnit *out);

/* —— 让"取最大"成为**显式决策**，而非静默行为（B2 强调）—— */
bool     om_partition_is_uniform(const OmPartitionHandle *h);
uint32_t om_partition_max_erase_unit(const OmPartitionHandle *h);

/* —— 不变式自检（两种模式都需要）—— */
OmRet    om_partition_is_erased(const OmPartitionHandle *h, uint32_t off, size_t len,
                                bool *out);
        /* 与 erasedValue 逐字节比较。模式 M 用它**校验引导侧的预擦**（不信任、可检测）；
         * 模式 R 用它**校验自己的擦除结果**（Zephyr NVS 的 nvs_flash_erase_sector 同款） */
```

**命名落定**：全部用 `om_partition_*`。**`OmMedia` 这个名字取消**——它要么等于分区句柄、要么等于 PAL 设备句柄，多出来的名字指同一件事（P2 佐证：littlefs 的 `partition` 一词在其头文件/SPEC/DESIGN/README 中**出现 0 次**，正因为它把这个概念下推成了回调；**而我们是有表的一方，就不该回避"分区"这个名字**）。

**"权限即防线"——2026-09-18 决定为【演进项，V1 不做】**：擦除权限本可作为**分区属性**声明（`meta` 不可擦、日志环可擦），使"应用侧永不擦 meta"从文档纪律变成运行期防线（对应本项目"两级防线"的一贯风格，见差距分析优势项 S-02）。

**V1 不做的理由**：靠既有纪律（写者只向"已擦副本" program）+ `is_erased` 自检已足够；且**该属性应与 §3.2 ② 的"分区能力声明"合并成一套能力位**，不该各做一套。**形态（加字段 vs 平行表）随 §5.2-3 一并定。**

**放弃的候选（2026-09-18 决定）**：

| 候选 | 决定 | 理由 |
|---|---|---|
| **`eraseTimeMax`（擦除最大耗时）** | **不进接口**（留文档） | 时序属性且随温度/磨损变化，**没有保证**——接口给出字段会暗示"这是保证"。缓冲预算仍按最坏值算，但那依据来自手册/实测，不是接口承诺 |
| **`allow_erase`（擦除权限 flag）** | **演进项，V1 不做** | 见上；V1 靠"写者只向已擦副本 program"的既有纪律 + `is_erased` 自检 |

**性质乙的 V1 清单（2026-09-18 定）**：**几何（数据，已在 PAL，需暴露）+ 窗口内擦除单位序列（派生，代码落地）+ 错误语义分层（约定，代码落地）+ `is_erased`（接口）**。

**契约与边界**：

| 项 | 约定 |
|---|---|
| 越界 | **`OM_ERR_RANGE`**（2026-09-19 用户决定："语义更明确"）。**与 `OM_ERR_INVALID_ARG` 的分界**：`RANGE` = **调用方请求**的地址区间越出可访问范围（**改偏移即可**）；`INVALID_ARG` = 参数为空 / 句柄伪造 / 未对齐 / **表配置错误**（**改表**，由 open / registry_validate 报出）。**越界优先于未对齐报出**。**不截断、不扩擦**不变。见下方"落地" |
| 未对齐 | `program` 非 `writeUnit` 整数倍 → `OM_ERR_INVALID_ARG`（器件层 `flash_write_validate` 已强制）；**`erase` 的两端必须落在扇区边界** → `OM_ERR_INVALID_ARG`——**⚠️ 本行原写"`erase` 非 `eraseUnit` 整数倍"，那是被否掉的标量**（非均一几何下不存在该标量）；正确表述同 `flash_erase_validate`：判"两端是否边界"，**不是模运算** |
| **并发** | 同一器件上 **`erase` 与 `program` 互斥**（F4 的 BSY 是**全局位**，RM0090 明文 "Write-while-write operations are not allowed"）⇒ 接缝**保证串行化**，但**时序安排归消费者**：模式 R 必须做到"擦除与应用写入**时间错开**"（K-38），且要知道**日志的擦除会占住整个器件的 BSY**，同器件的其他写入（meta / OTA staging）都得等 |
| 擦除中掉电 | 目标区状态未定义（PAL 既有语义）——**恢复是消费者的事务**，本接缝不提供 |
| 擦除失败 | `OM_ERR_IO`（单次失败）；"该区不可用、换下一区继续"的语义见 §4.3 |

### 4.3 错误语义分层（约定，而非新码）

| 情形 | 语义 | 现有码 | 业界对应 |
|---|---|---|---|
| 设备忙 / 队列满 | **稍后重试**（可恢复） | `OM_ERR_BUSY`(4) 或 `OM_ERR_AGAIN`(14) | pstore zone `-EBUSY` |
| 该区不可用（擦失败 / 后续坏块） | **换下一区继续**（局部降级，不整体失败） | **✅ 定：器件层发**（2026-09-19 用户决定）｜**落码 = `OM_ERR_FLASH_UNUSABLE`**（见下） | pstore zone `-ENOMSG` |
| 擦除/编程物理失败 | 单次 IO 失败 | `OM_ERR_IO`(11) | — |
| 格式/版本不兼容（将来） | **整体拒绝，不降级** | `OM_ERR_NOT_SUPPORTED`(5) 或专有别名 | UBI `-EINVAL` |
| 记录级校验失败（将来） | **只丢该记录**（与上一条**必须不同码**） | 需专有别名 | UBI `UBI_IO_BAD_HDR`；UBIFS 还多一个 `-EUCLEAN` |

**"格式不兼容"与"记录校验失败"必须用不同错误码**（调研 S2 的结论之一：否则消费者无法正确降级）；且二者都是 **fail-closed**，不得降级为"通过"。

#### 「换下一区」的落地：`OM_ERR_FLASH_UNUSABLE`（2026-09-19）

**① 错误码段更正（本表原写错了一处）**：原写"用模块别名 `0x001-0x0FF` 别名段"——**该段只把 `OM_ERR_<MODULE>_<NAME>` 映射到既有通用码**，而"该区不可用"**没有通用语义对应**（这正是它必须与 `OM_ERR_IO` 分开的原因）。⇒ 实际落 **模块特有码段 `0x1000+`**（`pal_flash_dev.h` 的 `OM_ERR_FLASH_BASE`，此前**预留未用**，本码是该段第一个使用者）：`OM_ERR_FLASH_UNUSABLE = OM_ERR_FLASH_BASE + 1`。

**② 与 `OM_ERR_IO` 的分界（这是它存在的全部理由）**：

| 码 | 含义 | 消费者策略 |
|---|---|---|
| `OM_ERR_FLASH_IO` | **这一次**操作失败（可能瞬态：总线干扰、时序） | **重试同一区** |
| `OM_ERR_FLASH_UNUSABLE` | **这块区**已验证不可用（结构性） | **跳过该区、换下一区继续** |

合用一个码则消费者**无从选择策略**——所以两行必须不同码，不是洁癖。

**③ ⚠️ 新决策：器件层「擦后校验」（超出原 §4.3 文本，如实记账）**

原 §4.3 的理由写的是"器件有第一手信息（**擦除返回失败**）"。但**擦除返回失败 ≠ 该区不可用**——它同样可能只是瞬态。要让这个码**真的有判据**，必须补一个检测机制：

> **擦除返回成功后，器件层读回比对 `erasedValue`；不通过即 `OM_ERR_FLASH_UNUSABLE`。**

- **为什么放器件层**：这是唯一能廉价发现"以为已擦"的地方。消费者若各自校验，**漏掉一处就是静默坏数据**——而"以为已擦"正是环形日志与引导元数据**最致命的假设**（写进未擦区 ⇒ 位与，数据静默损坏且 CRC 可能仍过）。
- **代价**：擦除是长操作（内部 flash 128K ≈ 1 s 级；SPI NOR 64K ≈ 100 ms 级），读回同段的代价约 **0.1%–7%**，相对擦除本身可忽略。
- **实现位置**：域 worker 内（`busy` 已置位、同域串行），读回不会与外部读交错。
- **免擦器件**（ER-1，`flash_geom_has_erase` 为假）无擦除语义，**跳过校验**。
- **单一判据**：`flash_geom_has_erase()` 是 `pal_flash_dev.h` 里的 `static inline`——**分区视图的能力位与器件层的擦后校验共用它**，不产生第二处定义。
- **测试**：sim 新增"静默擦失败"注入（报告成功但不落位），`partition_test` 断言 `om_partition_erase` 返 `OM_ERR_FLASH_UNUSABLE` 而非 `OM_OK`。

**④ 重试次数：默认 1，可配置（2026-09-20 用户决定）**

`OM_FLASH_ERASE_VERIFY_ATTEMPTS`（`pal_flash_dev.h`）——**"擦除 + 校验"为一轮的总尝试次数**：
- **默认 `1`**：只做一轮，首次校验未过即报 `UNUSABLE`（= 引入该机制时的原始行为）
- **`>1`**：**先重试再判死**

**为什么要有这个旋钮**：行业实证（本次调研，2,462 行一手取证）显示**"先重试再判死"是四家一致的做法**——CFI NOR 重试 3 次（`MAX_RETRIES 3`）、UBI 重试 3 次（`UBI_IO_RETRIES 3`）、JFFS2 用 refile 回路、**ESP-IDF NVS 重擦 2 次**（`CONFIG_NVS_FLASH_ERASE_ATTEMPTS` 默认 2）。**重试把"这次没成"与"这块区坏了"拉开距离**，`UNUSABLE` 这个判定的强度**随该值上升**。

⚠️ **语义随之变化，须记在明处**：该码始终表示"**在本配置的尝试次数内仍未达擦后值**"。默认 1 时它离"结构性不可用"较远，调大后才逼近。消费者若按"该区已废"处置，应先确认这个旋钮的取值。

**只对"校验未过"重试**；后端擦除**直接失败**属 IO 语义，不在此重试（归消费者策略）。

**越界 → `OM_ERR_RANGE` 的落地（2026-09-19，已改码 + 测试）**——**两层同时改**，否则同一条件两层报不同码，正是本文反复消灭的那种漂移：

| 位置 | 改动 |
|---|---|
| `partition.c` `partition_range` | 双端越界 → `OM_ERR_RANGE`；`partition_geom_check`（越器件容量）**刻意保持 `INVALID_ARG`**（表配置错，不是调用方越界）—— 两类行动主体已在源码注释里写死 |
| `hal_flash.c` `flash_read` / `flash_write_validate` / `flash_erase_validate` | 范围校验 → `OM_ERR_RANGE`；**未对齐 / 非扇区边界 → 保持 `INVALID_ARG`** |
| `pal_flash_dev.h` | 新增别名 `OM_ERR_FLASH_RANGE`；`OM_ERR_FLASH_INVALID_ARG` 注释去掉"越界"；三处 `@retval` 拆开 |
| `partition.h` | 偏移语义段与 `read` / `erase_range` 的 `@retval` 拆开，并写明"**越界先于对齐报出**" |
| `partition_test` / `flash_dev_test` | 越界断言改 `RANGE`；**新增"越界优先于未对齐"用例**（`off` 错位且长度越尾 → `RANGE`）钉住优先级 |

**验证**：`partition_test` **120 passed / 0 failed**；ARM 固件目标 `partition_verify` 构建通过。⚠️ `flash_dev_test` 的**运行**门禁早因既有崩溃摘除（另立项 **Issue #77**，提交 `36a9038` 明文"保留编译门禁、暂缓运行门禁"）⇒ 器件层的 RANGE 行为目前仅**编译验证**，其运行断言待 #77 修复后方能生效。

### 4.4 落位选项（**已定：C**，2026-09-18）

| 选项 | 做法 | 结论 |
|---|---|---|
| A. 扩展 partition | `open` 期把几何填入句柄 + 新增查询 API | 与 C 合并（见下） |
| B. 新接缝模块（`OmMedia`） | 独立模块持分区句柄 + 自取几何 | **否决**——与分区句柄概念重叠，多一个名字指同一件事（P2 佐证：littlefs 的 `partition` 一词出现 0 次，正因它把概念下推成回调；**我们是有表的一方**） |
| C. 消费者自取 | 各消费者自己 `flash_find` + `flash_geometry` | **否决**——正是 Zephyr littlefs 适配层的现状，代价已被实证 |

**定案 = "A 的形态 + 不做新层"**：**进 `partition`，几何给分区视图**；擦除单位的计算**内部写成纯函数**（将来若 boot 侧不经分区表，可直接暴露该函数而不必建表）。
