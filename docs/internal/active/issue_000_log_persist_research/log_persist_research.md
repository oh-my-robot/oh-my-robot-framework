## Part A. 需求分析

### A.1 消费者与场景（谁要它、要它干什么）

| # | 场景 | 诉求 | 对设计的直接约束 |
|---|---|---|---|
| S-1 | **赛后复现**（机器人失控 / 异常复位 / 行为不符预期） | 要知道"当时发生了什么"——**最近的**日志必须在掉电/复位后仍然存在 | 黑匣子语义：覆盖保新；异常复位路径不得丢数据 |
| S-2 | **崩溃现场**（fatal / 硬件 fault） | 保住崩溃前最后若干条 + 崩溃原因字串 + 关键寄存器 | fatal 上下文**不能写 flash**（见 C1/C5）→ 必须先落 RAM，复位后转存 |
| S-3 | **赛后分析导出** | 把日志搬到 PC 离线解析（RTT / 串口 / 调试器后门） | 设备侧只需"搬记录"的迭代 API；传输与解析格式解耦 |
| S-4 | **长期健康观测**（演进项） | 擦写计数、丢弃计数、介质健康 | V1 可只留计数与查询接口（对应差距分析 G-11） |

**场景优先级（待用户确认）**：S-1 与 S-2 是"黑匣子"的两条腿；S-3 是导出链路；S-4 可延后。

### A.2 硬约束（本仓既有架构决定，逐条有出处）

| # | 约束 | 出处 | 对持久化后端的含义 |
|---|---|---|---|
| C1 | **PAL 禁止在 ISR 上下文调用本族 API**；write/erase 为同步实现且内部等待**必须让出 CPU** | `lib/drivers/include/drivers/peripheral/flash/pal_flash_dev.h:212`（禁 ISR）、`:15`/`:90-92`（让出契约） | 持久化后端**不得**在中断/故障上下文触碰 flash 写路径 |
| C2 | **push 契约 = 文本分段流**：一次 push ≠ 一条日志，段缓冲 32B，行边界由 `\n` 承载；**module / level / 时间戳在 push 时已被格式化进文本** | `lib/services/include/services/log/log.h:55-64`；`lib/services/include/services/log/README.md`「消息形态」节 | ① 后端必须自己做**行组装**；② 若要"结构化记录头"（按模块筛选、机器可解析），当前接口**给不出** module/level 字段——只能解析文本头，或改接口（新增带元数据的钩子）。这是接口级事实，非取舍偏好 |
| C3 | **push 的调用上下文随裁剪配置而变**：异步模式（`OM_LOG_ASYNC=1`）恒在日志线程；**同步模式（=0）drain 落在生产者上下文**，而生产者可以是 ISR | `lib/services/src/log/ring.c:59-69`（现场 drain）、`lib/services/src/log/log_async.c:14-49`（线程路径）、`log.h:12-13`（中断上下文可调用） | 持久化后端在同步模式下**必须**把 push 做成纯 RAM 操作（拷贝进自有队列），否则 ISR 中打日志即违规（撞 C1） |

| C5 | **panic 钩子在故障上下文提交**（队列/线程/锁不可信） | `log.h:63` | panic 钩子内**不能**写 flash（撞 C1）→ 只能写 RAM 暂存区；转存是**复位后**的事 |
| C6 | **分区层为 v2 形态：注册表 + 句柄、模块零状态**；init 期 `om_partition_open` 一次，此后读写擦全走句柄；注册表须比实例活得久 | `lib/drivers/include/drivers/storage/partition.h:13-15`、`:63-69`、`:99-127` | 实例自身持有全部运行态（游标/计数）；init 顺序有依赖（open 必须先于任何写） |
| C7 | **不发明"存储统一层"**：日志层应声明自己的**窄接口**（append / 读回 / 重来 / 断点），实现可落在可擦族（环形+磨损）或块设备族；跨族选择在板配置/构建期绑定 | `docs/boot_ota/storage_landscape.md:120-124` | 持久化后端**对外是"流式追加后端"窄接口**；内部实现细节（扇区环/记录格式）不外泄为通用 API |

### A.6 容量与寿命粗算（把 NFR-3 / NFR-4 变成数字）

**真机几何**（`platform/bsp/vendor/STM32/STM32F4/adapters/flash/bsp_flash_f4.c:29-49`）：F427 每 bank = `{16K×4, 64K×1, 128K×7}`，F407 每 bank = `{16K×4, 64K×1, 128K×3}`；**最小编程单位 = 4 B 字**（`writeUnit = 4`，`:57`），无页聚合问题（SPI NOR 的 256 B 页在接入外部器件时才成为议题）。

**粗算假设**（**待 B-4 线核对后修正**，此处先给出可讨论的量级）：记录开销 ≈ 16 B/条，文本行均长 ≈ 80 B → **≈ 100 B/条**；擦写寿命按 10⁴ 次/扇区（STM32F4 片内的典型量级，**未查证手册，须核对**）。

| 分区尺寸 | 构成 | 可存记录 | 10 条/s | 1 条/s | 100 条/s（异常突发） |
|---|---|---|---|---|---|
| 64 KB | 4×16K 扇区 | ≈ 650 条 | 65 s | 11 min | 6.5 s |
| 128 KB | 8×16K **或** 1×128K | ≈ 1300 条 | 130 s | 22 min | 13 s |
| 256 KB | 2×128K | ≈ 2600 条 | 260 s | 43 min | 26 s |

**寿命**（口径：总可写条数 = 分区字节 ÷ 每条占用 × 擦写寿命；**扇区大小不影响寿命**）：

| 分区 | 介质与寿命 | 总可写条数 | @1 条/秒连续写 | @10 条/秒 |
|---|---|---|---|---|
| 64 KB | 片内（**10 k** 次） | ≈ 8.2×10⁶ | **≈ 95 天** | ≈ 9.5 天 |
| 64 KB | 外置 SPI NOR（**100 k** 次） | ≈ 8.2×10⁷ | ≈ 2.6 年 | ≈ 95 天 |
| 256 KB | 外置（100 k 次） | ≈ 3.3×10⁸ | ≈ 10.4 年 | ≈ 1 年 |

⇒ **修正**：寿命**不是**可以忽略的项。低速长跑（1 条/s，机器人常见）下片内 64 KB 只有约 **3 个月**；两个杠杆比任何算法优化都有效——**换外置 SPI NOR（×10）**与**加大分区**。

**四条直接结论**：

1. **片内 flash 装不下"全量日志"**。64 KB 只存得住**最近约 800 条**；10 条/s 的调试级流量 65 秒即写满。→ 落盘范围必须收窄（只收 WARN+ 或模块白名单），而这**正是已落地的 per-backend 模块过滤的用武之地**（`log.h:124-134`）。这不是可选优化，是容量决定的必需项。
2. **分区尺寸必须取 16K 扇区整数倍且 ≥2 块**（Q-1 的硬约束，两条独立理由）：
   - **语义理由**：若分区落进**单个 128K 扇区**，"环"退化为"写满即整区擦除"——**一次丢掉全部历史**，黑匣子语义破裂；
   - **时序理由**（B-4 线一手数据）：**STM32F4 的 128 KB 扇区擦除需 1.3–4 s 且期间 CPU 停转**（片内 XIP 取指受阻）。这个量级"单 bank 下不可接受"（B-4 原话）。16K 扇区把每次擦除的停转窗口缩小一个量级，是唯一现实选择。
3. **预擦必须提前"一整个扇区的写入时间"启动**，而不是提前几条记录：4 KB 扇区写满约需 36 ms，与一次擦除（典型 45 ms）**同量级**——按记录数触发预擦会在写满那一刻正好卡住。
4. **恢复扫描应默认走"只读扇区头 + 只扫最新扇区"**：全分区线性扫描 1 MB 约 105 ms（推算），优化后降到约 4 KB、亚毫秒且与分区大小基本无关。**但优化不豁免逐条 CRC 兜底**（扇区头有效 ≠ 数据完好），且**扫描期间再掉电是安全的**（只读）——这点优于任何"挂载时修复"的文件系统。

### A.7 Q-4 的仓内可行性：panic 暂存到底需要什么

**事实**：
1. 仓内**没有** NO_INIT / 免清零段基础设施——全仓检索唯一命中是 TI vendor 代码里的 IAR 语法（`platform/bsp/vendor/TI/MSPM0/.../dl_interrupt.c:44`），非框架设施。
2. 启动代码会**清零 .bss**：gcc 侧 `LoopFillZerobss`（`platform/bsp/boards/rm-a-board/startup/gcc/startup_stm32f427xx.s:83-95`），其边界符号 `_sbss`/`_ebss` 由链接脚本定义（`.../linker/gcc/stm32f427iihx.ld:232-243`）。
3. 每板双工具链各有一套：`linker/{gcc,arm}/` + `startup/{gcc,arm}/`（rm-a-board = F427、rm-c-board = F407）。

**推论**：STM32 的软复位（`NVIC_SystemReset`）**不清 SRAM**，所以所需的不是"掉电保持内存"，而是**免清零段**——把暂存区放在 `_sbss.._ebss` 区间之外，加 `__attribute__((section(".noinit")))` 即可存活过复位。**成本 = 每板 4 个文件（2 链接脚本 + 2 启动文件）× 2 板 = 8 处改动**，外加双工具链各验证一次。

**必须写死的边界**：这是**"复位保持"，不是"掉电保持"**。VDD 真正消失时 SRAM 内容全失——pstore/ramoops 有完全相同的边界（ramoops 只在 warm reboot 存活，持久化靠事后转存进 flash）。因此：

- **"掉电后仍有现场"只能靠复位后立刻转存到 flash**；
- 转存本身若再掉电，就是一个新的窗口——**这与业界同构，不是本设计的缺陷**，但要在文档里写明，避免"我们以为不会丢"的误判。

**暂存内容建议**：崩溃前 N 条日志 + `OmFatalContext`（已有 `file/line/pc/detail/reason/cause`，`lib/include/core/om_fatal.h:31-36`）。注意日志服务的消息环自身驻 `.bss`，复位后会被清零——要么把环搬进免清零段，要么在 fatal handler 里**先拷进暂存区**（纯内存操作，故障上下文可做）。

### B-1 Zephyr（已成稿）

> 430 行 / 含 F1–F7 事实、D1–D7 取舍、K/A/P 三类启示、U1–U12 存疑。以下为提炼。

#### B-1.1 架构与模式

- **三段式**：Frontend（`LOG_*` 宏）→ Core → Backends。
- **三种模式**（`LOG_MODE` 三选一）：**DEFERRED**（默认，内部走 `mpsc_pbuf` 多生产者单消费者缓冲 + 低优先级线程）、**IMMEDIATE**（同步，后端须支持互斥）、**MINIMAL**（仅编译期过滤，退化为 printk）。
- **实测栈开销**（Cortex-M3、2 参数）：deferred **40 B** vs immediate **412 B**——deferred 的调用侧成本优势是数量级的。
- **覆盖保新需显式开启**：消息缓冲默认丢弃；`CONFIG_LOG_MODE_OVERFLOW` 置 `MPSC_PBUF_MODE_OVERWRITE` 才是覆盖保新。
- **字典模式**：二进制输出 + `log_strings` 段，可整体剥离。

#### B-1.2 per-backend 过滤是**服务内建**能力

每个 source 一个 32 位 RAM 过滤器，切成 10 个 3-bit 槽（槽 0 聚合 + 9 个后端）；`log_filter_set(backend, domain, source, level)`，backend 传 NULL 即全部后端；shell 有 `log backend <name> enable/disable/status` 与 `log list_backends`。

⇒ 与我们已经落地的 per-backend 模块过滤（默认级 + 按模块覆盖）是**同一设计**，业界有同构先例。

#### B-1.3 两个持久化后端的命运（最值得读的一段）

| 后端 | 结局 | 争辩与缺陷 |
|---|---|---|
| **FCB 后端**（裸扇区环形） | **未进主线**：PR #28892（2020-10）request changes → stale → **2021-01 被 bot 自动关闭** | ① **过滤该谁管**——maintainer 明确"it should be done on logger level"，PR 作者误以为过滤是全局的，被纠正"logger supports independent filtering for each backend"；② **存什么**——"have you considered storing just the message? it would use much less space"，代价是 `%s` 指向 RAM，重复串会丢 |
| **FS/littlefs 后端** | **已进主线**（PR #32973，2021-03 合并） | 文件 `log.NNNN`（4 位、9999 回绕）；`FILE_SIZE` 默认 4096、`FILES_LIMIT` 默认 10、`OVERWRITE` 默认 y；**未挂载 → 静默丢弃**；`fs_write` 持续失败 → 进 `CORRUPTED` **静默停写且不 deactivate**；`BUILD_ASSERT` 禁 immediate；**无内建防递归**（flash 驱动自身打日志会挂死），官方规避是双后端 + 过滤或关掉 FS 日志 |

**⇒ 直接回应我们的 Q-2（存文本还是结构化）**：Zephyr 的 FCB 争辩给出了两边的真实代价——存"原始消息"省空间，但 `%s` 参数指向 RAM，**除非有字典/字符串表，否则字符串内容会丢**。这解释了为什么成熟实现在"省空间"与"可读"之间最终多选了格式化文本（或字典模式）。**我们的 push 契约给的是格式化文本（§A.2 C2），恰好落在被业界验证过的那一侧**；若要走结构化，必须同时解决字符串驻留问题。

#### B-1.4 panic 路径与 coredump

- `log_panic()`：强制 init → 通知各后端 → `while(log_process()){}` **忙等排空** → 才置 `panic_mode`。**core 里没有任何"后端处理中"的防递归标志**。
- 崩溃落盘走**独立子系统** coredump（`DEBUG_COREDUMP_BACKEND_FLASH_PARTITION`），带 header + checksum，并提供 `HAS_STORED_DUMP` / `VERIFY` / `COPY_STORED_DUMP` / `INVALIDATE` / `ERASE` 查询命令。
- **Nordic 官方建议：fatal handler 里别碰 QSPI，改为存 retained RAM、复位后再写。**

⇒ 这是继 NuttX CRASHDUMP 之后**第二条独立的一手依据**，支持我们 §A.7 的"免清零段暂存 + 复位后转存"路线，也支持"panic 路径不碰 flash"的硬约束（§A.2 C1/C5）。

#### B-1.5 两个否定性结论（同样有价值）

1. **ZMS/NVS 不能当日志后端**：无 `log_backend_zms`；Nordic 明确 ZMS "intended to store data in RRAM and not as a logging backend"；ZMS 文档**没有掉电原子性显式保证**。传统 flash 上官方推荐 NVS，而 NVS 是 KV 语义（见 B-2.5 反面教训 5）。
2. **Zephyr 主线至今没有"黑匣子语义"的持久化日志后端**：需求 issue #25907 自 2020-06 **至今 open**；#26295/#26296 当日即被 maintainer 判为重复关闭。**主线只有"FS 后端 + 独立 coredump 通道"**。

⇒ 含义：这个需求在成熟框架里**没有被解决**，我们不能指望"照抄某个成熟实现"；能照抄的是**零件**（FCB 的扇区环形、NVS 的状态位、coredump 的分区与校验），不是整体。这也解释了为什么旧稿的结论无法直接引用——业界没有可引用的收敛形态。

#### B-2.1 四种范式（业界实际收敛出的形态）

|---|---|---|---|

#### B-2.2 掉电安全手法（可直接借用的清单）

| 手法 | 代表 | 要点 |
|---|---|---|
| **状态表单向位编码** | EasyFlash ENV、FlashDB | 状态 = "从表尾往前找第一个 0 位"；推进状态只清 0，**状态 0（全 1）时根本不写 flash** |
| **按位置编码状态** | EasyFlash LOG | 三个 header 字，EMPTY/USING/FULL 对应"写到第几个字"，永不回头 |
| **多次单向写编码多值状态** | MCUboot swap status | 每扇区索引 3 条记录编码 4 个状态（`ff ff ff`→`01 ff ff`→`01 02 ff`→`01 02 03`） |
| **2 bit 条目状态位图** | ESP-IDF NVS | 页状态转换"只写 0"；**页头 CRC 故意排除 State 字段**（只覆盖 bytes 4–28），使状态可推进而无需重算 CRC |
| **PRE_WRITE → 数据 → WRITE 三段式** | EasyFlash、FlashDB、NVS | 只有终态被认作有效；中途掉电的记录扫描时标为 `ERR_HDR`/映射为 `UNUSED` |
| **先写新副本再删旧的** | FlashDB `move_kv` | 搬移中掉电旧记录仍有效，最坏是多一份而非丢一份 |
| **瞬态状态"下次上电续做"** | NVS `FREEING`、FlashDB `SECTOR_DIRTY_GC` | 官方语义：搬移在下次上电完成，而非回滚 |
| **撕裂写检测靠读"首字"** | NVS `load()` | 条目首字非 `0xffffffff` 即被写过 |
| **宁可多读也不误擦** | NVS `load()` | 注释理由：读整页比擦一次**快约 40 倍** |
| **崩溃时冲刷缓冲** | NuttX `sc_flush`（注释 "Flush buffered output (on crash)"）、ulog `ulog_flush` | 「异常时冲刷」被做进接口原生语义 |

#### B-2.3 对我们设计的直接映射（可直接采用的 8 条）

1. **记录帧自带 `len` + CRC + 单向"有效"位**，数据写完再置有效位——NOR 只能 1→0，这个位天然是不可逆的提交点。避免 EasyFlash LOG 那种"扫 0xFF 猜边界"的启发式。
2. **CRC 只覆盖不变部分（数据+长度），状态位在 CRC 覆盖范围之外**——学 NVS，否则每次推进状态都要重算 CRC，既多写又多一个撕裂窗口。
3. **环形覆盖以"块/扇区"为单位轮转**，而不是逐记录原地覆盖——天然对齐 flash 擦除粒度，掉电最多损失一块。**配合分区 v2，后端应维护一个"最旧块"水位**。
4. **显式的"最旧"锚点**（FlashDB `oldest_addr` 思路）：导出以该锚点为准，而不是"从头扫"。
5. **留"已导出"状态位**（FlashDB TSDB 的 `USER_STATUS1/2` 就是留给应用的）：导出只推进一个单向状态位，不改数据区、不额外磨损。
6. **排序键用单调序号，不用时间戳**——FlashDB TSDB **强制时间戳严格递增**，复位后时钟回退会**直接拒写**，这对无 RTC 的黑匣子是致命的。我们：序号排序，时间戳仅作参考信息。
7. **panic 路径只写固定小结构，不格式化字符串**；转存交给复位后的正常上下文（与 NuttX CRASHDUMP 一致）。
8. **容量按最坏情况给公式**——esp_coredump 明确定义"常量 20 B + 每任务 12 B（不含 TCB 与栈）"并给出最小值公式；我们应显式写出"单帧最大长度 × 期望条数 × 安全系数"。

#### B-2.4 我们 FR-5（panic 暂存）的权威依据

NuttX `CONFIG_BOARD_CRASHDUMP` 的 Kconfig 原文即："因为内存可能已被破坏，所以要**把机器状态保存到一个下次复位后能够由正常环境写入更精细存储的地方**"——这正是本稿 §A.7 推导出的结论，**有一手出处**。两个板级实现细节可直接照搬：CXD56xx 用 `up_backuplog_alloc("crash", ...)` 申请**独立备份 RAM 段**（非普通堆）；RX65N 用 **standby RAM（SBRAM）**。

另有两条接口级佐证：「崩溃时冲刷缓冲」在 NuttX 是 `syslog_channel_s::sc_flush` 的原生语义、在 ulog 是 `ulog_flush()`——**我们的 log 服务必须有等价 flush 原语并与 panic 钩子对接**（服务已有 `flush` 钩子位，见 §A.2 C4）。

#### B-2.5 反面教训（本次调研最该吸收的五条）

1. **"一个扇区出错就擦掉整个日志区"——黑匣子场景的灾难**。EasyFlash LOG 的 `find_start_and_end_addr()` 遇到任何状态序列非法、扇区头读不出、或 USING 扇区数不为 1，就 `ef_log_clean()` 全擦；RT-Thread 论坛有"写日志时掉电 → 上电全部日志被清"的实测报告（机制已在源码中独立确认）。**我们必须反过来：逐块隔离，坏块只丢自己，能读的一律保留，导出时明确报告"N 块损坏"。**
2. **"决策表式"恢复逻辑会变砖**。MCUboot 用 trailer 状态组合匹配决策表；掉电落在**表未覆盖的中间态**时它既不回滚也不启动备用，直接把设备变砖（PR #2100）。→ **恢复逻辑要么是全序状态机且明确处理每个中间态，要么保证"任何未知组合都有安全默认值"**——绝不能让"没匹配上"等于"什么都不做"。
3. **元数据/Trailer 单点反复写且无磨损处理 = 公认弱点**。MCUboot trailer 如此；STM32U5 SBSFU 移植中还因 flash 驱动未重定位 Bank2 页号导致该扇区从未擦除、trailer 写入被直接拒绝。→ **任何"反复改写的固定位置"都要有轮转方案，且必须有"写入被拒"的错误路径。**
4. **不要在日志回调里做阻塞文件 IO**。ESP-IDF 官方 issue #13205：用 `esp_log_set_vprintf` 写 SPIFFS 导致其他任务栈溢出；ulog 官方也警告**需要挂起的后端（Flash/网络）在 idle 线程里不可用**。→ 独立写线程 + 有界队列 + 批量落盘是正确架构。
5. **KV 库的"满了"行为 ≠ 黑匣子**。NVS 满了是 `ESP_ERR_NVS_NO_FREE_PAGES` **报错**，不覆盖最旧；拿 KV 语义当黑匣子会在写满那刻开始静默丢**最新**日志。→ "环形覆盖保新"必须显式实现并显式测试。

另两条边界：**文件系统不解决掉电原子性**（NuttX 文件通道要求 FS 已挂载，因此"cannot be supported during the boot-up phase"——启动早期与崩溃时刻都指望不上）；**异步模式没有 flush 原语就是不合格**（ulog 官方原话：hardfault 与断言会丢日志）。

**B-2 存疑项（14 条，勿作设计依据）**：FlashDB 官方文档站为客户端渲染抓不到正文（机制描述全部改由源码支撑）；NVS 页状态的具体数值未从源码证实（`nvs_constants.h` 两个 ref 均 404）；EasyFlash 设计文档**完全未覆盖 LOG 模块**；EasyFlash LOG 单条半写的截断行为属机制推断、未经故障注入验证；`ulog_easyflash` 是否补了记录级 CRC 未证实。详见原始材料。

### B-3 Linux / Android / 车规（已成稿）

> 932 行 / 341 条出处链接 / 含五维对照表 + 可借鉴 A–G + 应避免 10 条 + 28 条存疑。**本线修正了我方任务书里的若干错误预设**（见 B-3.6）。

#### B-3.1 pstore：与我们的转存接缝**逐层同构**

pstore 的形态是「通用前端 + 可插拔后端」，可与我们的结构逐层对齐：

| pstore 层 | 职责 | 我方对应物 |
|---|---|---|
| **前端**（dmesg / console / pmsg / ftrace） | 定义"什么需要跨重启存活"，各自独立开关 | 日志类别/来源（系统日志、panic 现场、用户态事件） |
| **核心**（`fs/pstore/platform.c`） | 记录命名、压缩、erase 语义、panic 并发策略 | log 服务的记录管理层（命名、CRC、序号、回收语义） |
| **后端**（ramoops / pstore-blk / efi） | 只负责"把一段字节写进某持久介质并读回/擦除"，经 `open/close/read/write/erase` 注册 | **flash 分区后端**（分区 v2 句柄）+ **保留 RAM 后端**（panic 暂存区） |
| **转存者**（systemd-pstore / recovery-persist / BootReceiver） | 下次启动读空持久区、归档、**清空以便下次事件** | **我们的"转存接缝"** |

**可直接借鉴的四点**：

1. **后端 = 填一张函数指针表**（`open/close/read/write/erase`），上层不知道介质细节；且 pstore 允许后端只实现最小集合（不提供 `write` 时核心转发到 `write_buf`）——**对 MCU 上做分级后端很有用**。
2. **记录命名带三元组** `类型-后端名-序号`（`dmesg-ramoops-0` 里的 `ramoops` 是**后端名**）⇒ 建议我们的**记录头带 `backend_id`**，让导出侧能标注"这条是复位后转存来的"还是"直接写 flash 的"。
3. **「转存接缝」的正确语义 = 读走 → 归档 → 清空（三步）**。`pstore.conf` 的 `Unlink=` 默认 true，设计目的被明确写成"让 pstore 保持近乎空的状态，以便下次内核错误事件有空间可用"——**清空不是可选项，而是"下一次崩溃还能记"的前提**。
4. **保留 RAM 区的有效性协议照搬 ramoops**：zone 头含 magic `"DBGC"` + `start` + `size`，四条分支（空/无效/有效保留/全新）逻辑清晰，**头部不带时间戳，"是不是新的一次启动"完全由 magic + size/start 合法性决定**——正好解决"复位后无法确定保留区里是上次现场还是上电随机值"的问题。再叠加 **Reed-Solomon ECC**（128 B 块 / 16 B 校验）应对看门狗复位后的 RAM 半损坏。

**反面参照（重要）**：ramoops 的计数器**重启即清零**，新 dump 会覆盖更早的——"**如果转存没来得及做就被新一次崩溃覆盖，现场就永久丢了**"。⇒ 我方转存必须在**尽可能早**的启动阶段完成；且建议保留区用**多条 slot**（像 ramoops 的 `max_dump_cnt`）而不是单条，**容忍"上一次还没转存又崩了一次"**。

#### B-3.2 「panic 不能直接写 flash」——内核有成文规则

**pstore/blk 六条硬约束**（可直接当我方"保留 RAM 暂存区写入代码"的检查清单）：① 不能分配任何内存（init 时分配好）；② 必须轮询、不得睡眠；③ 不能拿任何锁（"你被允许打破所有锁"）；④ 用 CPU 拷贝、避免 DMA；⑤ 直接控制寄存器；⑥ 状态不明时重置设备。

**mtdpstore 三条"panic 不能做"**（对**复位后转存路径**同样有约束力）：
- **panic 时不能擦除** → 所以**正常路径要保证至少一个已擦 zone 待命**（源码注释原话 "As there is no erase for panic case, we should ensure at least one zone is writable."）——这与 B-4.7 的"维持至少一个已擦扇区不变式"是**同一条**，两条独立来源相互印证；
- **panic 时不能探坏块** → 正常路径**预先维护 `badmap` 位图**；
- **擦除要"懒"**：只有整个 block 都空闲时才擦，否则记入 `rmmap` 等 flush 时"读出有效数据→擦块→写回"（注释 "Avoiding over erasing..."）——**对片内 NOR 的磨损均匀与写放大控制直接可用**。

旁证：内核给块设备加 `panic_write` 时明确指出通用块写路径**不可用因为"会睡眠"**，只能改用静态预留 bio + 轮询，且不能用 `REQ_PREFLUSH`——**与我方"flash 写必须让出 CPU → panic 上下文不能写 flash"是同一物理约束的两种表述**。作者同时声明这**不是**驱动原生 panic 钩子的替代品（即业界也认为轮询写只是 best-effort）。

#### B-3.3 记录格式：建议选"自描述 + 关键帧"这一支

- **ArduPilot 范式（主结构）**：3 字节记录头（`0xA3 0x95` + `msgid`）+ **FMT 自描述消息**（type/length/name/format/labels），FMT 自身固定 `msgid=128`——**导出工具不需要任何编译期信息就能解出全部字段名与类型**。我方可在分区开头固定写一条"格式表记录"，解析侧先读表再解流；单位/缩放用独立的 `UNIT`/`MULT` 消息（官方明确警告"不要从单位名推断缩放"，**缩放因子要显式写进格式表**）。
- **Betaflight 范式（重同步锚点）**：I 帧（自包含关键帧）+ P 帧（差分）；I 帧的存在理由**不是压缩率**，而是注释原话 "Write a keyframe every blackboxIInterval frames so we can **resynchronise upon missing frames**"。⇒ 我们若做任何压缩，**必须同时保留"重同步锚点"语义**，否则一次损坏会污染其后所有记录。
- **两遍式解析（header 先行）**：先跑 header 循环建立字段表 → 再跑 payload 循环逐帧解。**"先建表、再解流"应作为我们导出/离线解析工具的标准结构**。

#### B-3.4 可靠性：把"序号"与"校验"分开

- **OPC UA Part 14 §7.2.3 给出成熟的回绕序号窗口判定公式**（下界 `2^(N−2)`、上界 `2^N − 2^(N−2)`）。环形缓冲的序号必然回绕，**应照此实现，而不是简单比大小**。
- **反例**：AUTOSAR DLT 只有 8 位 MCNT 序号、**且完全没有 CRC**——它提醒我们：**序号解决"连续性"，CRC 解决"完整性"，两者不可互相替代**。
- **"干燥收尾"标志（低成本高价值）**：Betaflight 正常 disarm 时写 `'E', 0xFF, "End of log", 0x00`，掉电时这条不会写入——**一个字节就能区分"上次是正常结束还是异常掉电"**，从而决定是否需要走恢复/转存。**比 CRC 更便宜，且直接驱动状态机**。
- **journald 的教训（状态字段）**：它判定"文件是否干净关闭"**唯一**依据是 header 的 `state` 字段，且状态翻转**前后各一次 fsync**；但早期版本因 `set_offline()` 在 state ≠ ONLINE 时短路，导致**被轮转的文件从不被 fsync**——"一个看起来对的状态机能静默地让某类文件永远不落盘"。⇒ 我方若引入"分区状态字段"，**必须对每条状态迁移路径逐一验证"该落盘的都落盘了"**。

#### B-3.5 轮转、限额与导出

- **"环形覆盖最老"有法规与工程双重支持**：ramoops 轮转、pstore/blk chunk 覆盖、ArduPilot 块后端（注释 "we're a ring buffer and never run out of space"）、UN R160 5.3.4"无空缓冲时 FIFO 覆盖"、49 CFR §229.135 铁路"记录最近 48 小时"。
- **但"保新"有一条底线**：ArduPilot 官方文档写明 "If there is only one file on the flash when space runs out, **logging is stopped instead**"——**连它也不敢把最后一份数据擦掉**。我们的环形覆盖必须保留同一条底线（**至少留一条最近记录**），否则"保新"会退化成"什么都留不下"。
- **"标记为重要"的记录应豁免覆盖**：车规 EDR 要求气囊展开事件 "must be locked to prevent any future overwriting"，而 UN R160 又规定无空缓冲时 FIFO 覆盖——两者结合的正确解读是：**默认环形覆盖保新 + 重要记录可 pin**。我方可以加一个 `pinned` 位，或保留一个专用的"最后一次致命故障" slot 不受轮转影响。
- **导出协议照抄 ArduPilot**（本线最值得照抄的一条）：
  - `LOG_REQUEST_DATA` **带 `ofs` + `count`，天然分包 + 断点续传**；**导出状态全部在主机侧**（设备不需维护"当前导出位置"）——对 MCU 内存极度友好；
  - **"完成"的判据是"收满 `LOG_ENTRY` 报告的 `size`"，而不是"某一包返回 0 字节"**（官方明确这是唯一可靠判据）；
  - **同一时刻只允许一个未完成的下载请求**（多余请求静默忽略），但丢包可以事后用另一个请求只补那个偏移区间；
  - **解析工具必须容忍残缺尾部**：pymavlink 的注释原话 "we can have garbage at the end of an APM2 log"、"out of data - can often happen half way through a message" ⇒ **"尽力解析可解析的部分"是硬性要求**——黑匣子的尾部必然是残缺的；
  - **关键帧/会话起始偏移表应在写入时持久化**（Betaflight 网页版每 4 个 I 帧切 chunk 并快照状态，注释 "To enable seeking to an arbitrary point in the log without re-reading anything that came before"），否则导出要全分区扫描。

#### B-3.6 应避免（10 条中最相关的 7 条）

1. **不要指望"临时文件 + rename"保原子性**——journald **不是**这么做的（该说法在 systemd 源码中不存在），它用"原地写 + state 字段 + 前后各一次 fsync"；NOR 上更没有 rename 语义。应明确采用 **写入 → CRC 校验 → 提交标记**，且**提交标记必须是最后一个写下的字节**。
2. **不要忽略"计数/状态重启清零"导致的覆盖**（ramoops）——复位转存必须抢在任何新写入之前完成。
3. **不要硬编码记录名/偏移**（pstore 文件名含后端名）——导出工具应通过格式表/分区表解析。
4. **不要默认"大 record_size 就能存下完整现场"**：LKML 讨论指出 4 MB 的 `record_size` 直接失败、2 MB 会丢一半 dmesg，**且讨论没有产出解决方案**。⇒ 现场暂存区大小按实测最坏情况定，**并默认接受截断**（ramoops 语义：超出即丢，不续写）。
5. **不要用"元数据每写必更新"换可恢复性**：Betaflight 明确拒绝写卷头，理由是 "keeping a header up to date while logging would incur more writes to the flash, which would consume precious write bandwidth and block more often." ⇒ **与我们零状态分区表 v2 的取舍方向一致，应保持**：恢复靠扫描/魔数，不靠每次更新的头。
6. **不要在 panic 路径做任何可能失败的重试或加锁**：pstore 用 `trylock`，抢不到就**直接放弃本次转储**——宁丢一条，不卡死系统。
7. **不要在跨启动的全局序上偷懒**：journald 的 seqnum 每次启动重置为 0，跨 boot 强行做全序会产生 A<B<C<A 的环。⇒ 若用 `(boot_id, seq)` 二元组，**导出时必须保留 boot_id，"最新记录"的判定也必须以 boot 序为准**。

另有一条方法论警示：journald 的 man 页把 `SystemKeepFree` 默认写成 15%，**自 v243 起代码实为 5%**——**涉及默认值的结论必须查源码而非文档**。

#### B-3.7 本线对任务书预设的修正（诚实性记录）

调研推翻了我在派单时给出的几处说法，均已按一手来源更正：journald **不存在**"rsync 式临时文件 + rename"；内核**不存在** `drivers/soc/qcom/pmsg.c`（pmsg 在 `fs/pstore/pmsg.c`）；Android **不存在** `persistent` log buffer id；ArduPilot 记录头是 **3 字节**（非 2 字节）；ArduPilot 与 Betaflight **都没有**"块头含首次写该扇区序号"的字段。另有两个我在派单里给的 URL 已 404（Betaflight 文档入口与 Android logging 文档），由该线自行更正。

### B-4 flash 横切技术（已成稿）

> 508 行 / 含器件时序、布局手法、恢复扫描、掉电窗口、磨损寿命、CRC 选型、量化启示、U1–U12 存疑。**注意：本线所有容量/寿命/扫描耗时数字均为推算，需在目标板实测。**

#### B-4.1 选型结论：裸分区环形，**不引入文件系统**

三条独立的一手论据：

1. **littlefs 维护者自己的建议**：日志这种关键路径应 "reserving a fixed amount of raw flash to hold the log"，因为 "any filesystem will necessarily be slower"；
2. **ESP-IDF 官方**把 NVS 标为 "not suitable for logging"；SPIFFS 的掉电韧性仅标 "Partial"，且只能可靠利用 75% 分区；
3. **语义本就不匹配**：我们的目标是**覆盖保新**（黑匣子），文件系统提供的是**持久不丢**（POSIX）——用 FS 等于付 COW/GC/目录元数据的代价，买一个我们不需要的保证。

但要**保留 FS 的可取零件**：littlefs 的"双份 + CRC + revision"与 MCUboot 的"魔术字最后写"，都能在裸分区里按需复刻，成本只有几个字节。

#### B-4.2 器件数字（一手，**设计必须按最大值而非典型值**）

| 介质 | 擦除 | 编程 | 寿命 |
|---|---|---|---|
| 外置 W25Q128（4 KB 扇区） | 典型 45–100 ms / **最大 400 ms** | 0.7 ms 典型 / 3 ms 最大 | **100 k 次/扇区** |
| 片内 STM32F4（**128 KB 扇区**） | **1.3–4 s，且 CPU 停转** | — | **10 k 次** |
| 片内 nRF52840（4 KB 页） | 最大 85 ms，**停 CPU** | — | — |

**两条血泪教训**（均有现场/一手出处）：
- **绝不能按典型值做超时**：nRF52832 页擦除 typ 2.05 ms vs **max 89.7 ms（44 倍差）**；W25Q128 现场实测 25 °C 约 50 ms、**>60 °C 达 300 ms**，有人用 100 ms 超时 → 写入半擦除扇区 → 数据损坏；
- **擦除后要验证擦干净**（与 `erasedValue` 逐字节比较），W25Q128 那起故障正是"没验证擦除结果"造成的。

外置 SPI NOR 的擦除是**器件自持**的（发命令后器件自己干），CPU 只需轮询 WIP 或挂起——这正好匹配我们器件层"写必须让出 CPU"的抽象：实现为**异步提交 + 完成通知**，日志 API 即可非阻塞。片内则不同：**CPU 真的停转**（XIP 取指受阻），只能靠 RAM 缓冲接住。

#### B-4.3 记录布局（综合四个实现收敛出的形态）

```
[扇区头] magic(4) | ver(1) | seq(4) | hdr_crc(2)   ← 首写；全 0xFF = 未使用
[记录 0] magic(2) | len(2) | seq(4) | crc(4) | payload(...)
...
[扇区尾全 0xFF]                                     ← 扫描到此即写游标
```

- **记录不跨扇区**——pw_kvs 给出一手理由：跨扇区则"擦一个会毁掉该条目"。代价是单条上限 = 扇区大小 − 头；对几十~几百字节的记录，16 KB 扇区绰绰有余。
- **提交顺序是原子性的唯一来源**：payload 先写 → 记录头（含 len 与 crc）后写 → 这样"头未写"的状态天然是全 0xFF/魔术字不匹配，扫描时判为空。FCB、Zephyr NVS、ESP-IDF NVS 位图、MCUboot trailer **四种实现等价**。
- **不要持久化 read/write 指针**：指针本身是需要原子提交的元数据，多一个掉电窗口。**改为扫描重建游标**。
- **扇区尾写 `len=0` 结束标记**，避免"空白区"与"半写"混淆（FCB 有同类机制）。

#### B-4.4 恢复扫描：默认走优化路径

| 路径 | 代价 | 说明 |
|---|---|---|
| 朴素全扫 | 64 KB ≈ 3 ms / 1 MB ≈ 105 ms（推算） | O(分区) |
| **优化：只读扇区头 + 只全扫最新扇区** | 16 个头 × 8 B + 1 个扇区 ≈ **4.1 KB，亚毫秒，与分区大小无关** | **本设计应采取的默认路径** |

优化**引入三个必须显式处理的风险**：① 扇区头有效 ≠ 数据完好 → **仍须逐条 CRC 兜底**；② "头已写、记录未写"的窗口 → 扫到空扇区要能回退到前一扇区当活动扇区；③ 若为更快而缓存"最新位置索引"，该索引又变成需要原子提交的元数据——**建议不缓存，永远靠扫描**。

**扫描期间再掉电是安全的**（只读无写）——这点优于任何"挂载时修复"的文件系统（SPIFFS 的 check 会改 flash，littlefs 的 GC 也会写）。

#### B-4.5 擦写时序与错峰（关键洞察）

- **4 KB 扇区装 51 条 80 B 记录，写满约需 36 ms，与一次擦除（典型 45 ms）同量级** ⇒ **erase-ahead 必须提前约"一整个扇区的写入时间"启动**，按记录数触发会在写满那刻正好卡住。
- 最坏情况（400 ms 擦除）下 @100 条/s 要缓冲 **约 40 条 / 3.2 KB** ⇒ 缓冲预算要按**最大**擦除时间算。
- **多条记录应合批到同一页**（页编程 0.7–3 ms/次），**不要每条日志一次编程**。

**补：片内 16 KB 扇区的擦除时间**。本轮未取到数值——STM32F427/429 datasheet 的 **Table 48（Flash memory programming）** 定义了 `t_ERASE16KB`，需查手册原文（128 KB 的 1.3–4 s 已由 B-4 给出）。**旁证**：Zephyr 的 STM32 flash 驱动把超时写成 `STM32_FLASH_TIMEOUT = 2 × devicetree 的 max_erase_time`（注释原话 "wait for double the max erase time to be sure"），且**该超时不区分扇区大小、擦与编程共用一个值**——即业界同样是**只信最大值**，与我们"不要用典型值做超时"的结论一致（来源：`zephyr/drivers/flash/flash_stm32.c`）。

#### B-4.6 CRC 选型

- **记录级 CRC-32，扇区头 CRC-16/CRC-8**（分层，同 Zephyr NVS）。
- 算过账：全生命周期 8.19×10⁶ 条时，CRC16 随机漏检期望 **~125 条**、CRC32 **~0.002 条**；代价仅每条多 2 B（**容量少 2.3%**）。**用 2.3% 容量换 5 个数量级可信度，值得。**
- **坑**：STM32 硬件 CRC 是 **CRC-32/MPEG-2**（poly 0x4C11DB7），**不等价于 zlib CRC32**——若导出到 PC 用 zlib 校验，要么软件实现，要么在格式文档里写明变体。CPU 代价可忽略（1 HCLK/字节，相对 0.7 ms 页编程是 1e-5 量级）。

#### B-4.7 其余对本项目的直接约束

1. **不要用典型擦除时间做超时**；超时必须走错误路径（不写半擦除扇区）。
2. **擦除失败要能降级**：NOR 无坏块表，但单次失败真实存在 → 擦除失败则**标记该扇区跳过、用剩余扇区继续环形**（容量下降但不死）。
3. **维持"至少一个已擦扇区"不变式**——FCB/NVS/pw_kvs 都依赖它做轮转，这正是 erase-ahead 要维持的。
4. **seq 回绕用序列算术**比较（`(int32_t)(a-b) > 0`），32 位下先磨损坏而非回绕。
5. **RAM 预算可做很小**：裸环形只需一个扇区大小的写缓冲（16 KB 扇区下需斟酌）或按记录缓冲 + 未刷盘队列。
6. **器件层需要的不只是"分区内偏移读写擦"**：还需要**擦除/编程的异步完成通知**，否则上层会因自旋等待而阻塞（对应 §C.2 的 W-1/W-2 选项）。

**B-4 存疑项（12 条）**：W25Q128 的 45 ms 典型值仅见转述（datasheet 另有 100 ms 说法，最大同为 400 ms，**设计按 400 ms 即可**）；100 k 寿命未见 Winbond 官方 PDF；**所有扫描耗时/容量/寿命数字均为推算**（读带宽 10/20 MB/s 是粗估）；SPIFFS 劣化具体数字无原始测试条件。详见原始材料。

**§C.1 结构化记录头的改造成本（对应 Q-2）**

事实：`OmLogMsg` **确实携带** `module`（含名字与 moduleId）、`level`、`ts`（生产时刻单调 ms）（`lib/services/src/log/log_internal.h:74-82`）；但扇出到后端的只有格式化后的文本段（`log_backend_push_mask(mask, seg, len)`，`log_internal.h:225-229`）。

因此"记录里要带结构化 moduleId/level/时间戳"只有两条路：

| 方案 | 做法 | 成本 | 代价 |
|---|---|---|---|
| **T-1 解析文本头** | 持久化后端自己解析 `[LVL][HH:MM:SS.mmm][module] ` 前缀 | 零接口改动；约几十行解析 | 格式一旦调整即静默失配；模块名→id 映射要自建；时间戳只有 ms 分辨率且**已转成文本** |
| **T-2 接口扩展** | 在 `OmLogBackend` 增**可选**的"每条消息开始"钩子（如 `begin(backend, module, level, ts)`），`log_emit_args` 在格式化前调用一次 | 改动面 = `log.h`（+1 可选字段）+ `backend.c`/`core.c` 各一处；现有 RTT/串口后端置 NULL 即不受影响 | 公共头契约变更（需过评审）；增加一次 per-message 间接调用 |

**建议**：若"读侧按模块筛选"是真实需求（而非想象需求），选 T-2——它把格式知识留在服务侧；若 V1 只要人读文本，选不选都行，可先不做。**这一条取决于用户对 S-3 导出形态的预期**。

**§C.2 「谁来做写者」的三个选项（裁决 6 的重估材料）**

事实基线：每个 flash 设备注册时建**一个执行域 worker 线程，栈 3072 B**（`lib/drivers/src/peripheral/flash/hal_flash.c:381`）；域 worker 完成回调里**允许再提交异步请求**（`pal_flash_dev.h:206-207`）；无 OSAL 编译时异步 API 返回 `OM_ERR_NOT_SUPPORTED`（`pal_flash_dev.h:252`）。

| 选项 | 形态 | 代价 / 风险 |
|---|---|---|
| **W-1 专用写线程**（旧稿裁决 6） | push 只入自有 RAM 队列；写线程取队列→行组装→记录打包→游标/预擦调度→提交分区写 | **+1 线程**（栈按域 worker 参照约 3 KB 量级）+ 队列 RAM；换来最可控的时序与最小的域占用 |
| **W-2 骑器件域 worker（自时钟链）** | push 只入 RAM 队列；提交异步写；在 done 回调里取下一批再提交（回调内再提交是**契约明确允许**的） | **不新增线程**；但 ① 占用共享 worker，可能饿死同域其他设备 ② 写流水期间**读被 busy 协议拒绝**（`pal_flash_dev.h:210-211`）——导出/恢复扫描会被拖住 ③ 设备级 done 回调是**单槽**（`flash_set_done_cb`），与同设备其他异步使用者天然互斥 |
| **W-3 无 OSAL 退化** | 既无 worker 也无日志线程 → 只能在 flush 点同步写 | 掉电窗口 = 自上次 flush 以来的**全部**日志（与 NFR-5「可预期的小窗口」冲突）；仅在无 OSAL 形态下成立 |

**倾向**：W-1 与"不发明统一层"（C7）不冲突——它承载的是**日志语义**（行组装/记录打包/游标/预擦轮转），不是通用存储管理；但**必须先确认**同步模式（`OM_LOG_ASYNC=0`）下 W-1 的线程从哪来（这也是 Q-3 的实质）。若 Q-3 选"退化"，则 W-3 是唯一形态。

## Part D. 调研结论

> 本节只做两件事：把**依据充分、可直接进设计**的结论挑出来；把**仍有分支、需要拍板**的取舍列清楚。**不代替设计稿**——设计稿是下一步的产物。

### D.1 确定性结论（多来源收敛，可直接进设计）

| # | 结论 | 依据 |
|---|---|---|
| 1 | **裸分区做记录环，不引入文件系统** | littlefs 维护者建议 + ESP-IDF 官方对 NVS/SPIFFS 的定性 + 语义不匹配（覆盖保新 vs 持久不丢）——三条独立论据（B-4.1） |
| 2 | **记录不跨扇区** | pw_kvs 给出理由（跨扇区则擦一个会毁掉该条目）；FCB 等实现一致（B-4.3） |
| 3 | **提交顺序 = 原子性的唯一来源**：payload 先写，含 len/CRC 的记录头后写 | FCB / Zephyr NVS / ESP-IDF NVS / MCUboot trailer 四种等价做法（B-2.2、B-4.3） |
| 4 | **不持久化读/写指针，靠扫描重建游标** | B-4.3；且扫描可压到亚毫秒（B-4.4） |
| 5 | **记录级 CRC-32 值得**（+2 B 换 5 个数量级可信度）；**扇区头用 CRC-16/8** | B-4.6 的期望漏检计算 |
| 6 | **片内取 16K 扇区、分区 ≥2 块** | 语义（避免整区擦除）+ 时序（128 KB 擦除 1.3–4 s 且停 CPU）（§A.6、B-4.2） |
| 7 | **绝不接受"一个扇区出错就全擦"**——逐块隔离，坏块只丢自己 | EasyFlash LOG 的实测反面教训（B-2.5-1） |
| 8 | **排序键用单调序号，时间戳仅作参考** | FlashDB TSDB 强制时间戳递增 → 时钟回退直接拒写（B-2.3-6） |
| 9 | **panic 路径只写 RAM 暂存，复位后转存** | NuttX CRASHDUMP 的 Kconfig 原文 + Nordic 对 Zephyr 的官方建议，两条独立一手依据（B-1.4、B-2.4） |
| 10 | **"写必须让出 CPU"要落成异步提交 + 完成通知**，日志 API 才可能非阻塞 | 外置 NOR 擦除为器件自持；片内则 CPU 真停转（B-4.2） |
| 11 | **按最大值而非典型值做超时** | nRF52832 typ/max 差 44 倍；W25Q128 高温下 50→300 ms 的现场故障；Zephyr 以 `2 × max_erase_time` 做超时（B-4.2 及补注） |
| 12 | **顺序轮转天然均匀磨损，无需额外均衡算法** | B-4 的寿命口径：每扇区每轮转恰好擦一次（**修正**旧稿裁决 8 的"无需 FTL 级映射"为有据） |
| 13 | **panic 路径只做"CPU 拷贝 + 校验 + magic/长度头"，完全不碰 flash 驱动** | pstore/blk 六条成文约束 + mtdpstore 三条（B-3.2） |
| 14 | **正常路径必须保证"至少一个已擦扇区待命"**（panic 时不能擦除） | mtdpstore 源码注释原文；与 B-4.7 的"至少一个已擦扇区"不变式**两条独立来源相互印证**（B-3.2） |
| 15 | **转存接缝 = 读走 → 归档 → 清空三步**，且**清空是"下次还能记"的前提** | systemd-pstore 的设计目的（B-3.1） |
| 16 | **保留区用多条 slot，容忍"上次没转存又崩一次"** | ramoops 计数器重启清零 → 新 dump 覆盖旧 dump（B-3.1） |
| 17 | **引入"干燥收尾"哨兵**，用一个字节区分"正常结束 vs 异常掉电" | Betaflight 的 `'E'` 结束标记（B-3.4）——比 CRC 更便宜且直接驱动状态机 |
| 18 | **序号与校验职责分离**：序号管连续性（回绕用窗口判定），CRC 管完整性 | OPC UA Part 14 §7.2.3 公式；反例 DLT 有 8 位序号却无 CRC（B-3.4） |
| 19 | **导出协议采用"请求带偏移+长度"形态**，导出状态全部留在主机侧 | ArduPilot `LOG_REQUEST_DATA`（ofs+count）天然断点续传，对 MCU 内存友好（B-3.5） |
| 20 | **"保新"有底线：至少保留一条最近记录**，不得把最后一份数据擦掉 | ArduPilot 官方："if there is only one file… logging is stopped instead"（B-3.5） |
| 21 | **重要记录可 pin，豁免环形覆盖** | 车规 EDR 的"锁存不可覆盖" + UN R160 的 FIFO 覆盖，两者结合的解读（B-3.5） |
| 22 | **导出/解析工具必须容忍残缺尾部**——"尽力解析可解析的部分" | pymavlink `DFReader.py` 的注释与实现（B-3.5） |

### D.2 仍有分支的取舍（需拍板，不宜由调研单方面决定）

| 取舍 | 选项 | 调研给出的倾向 |
|---|---|---|
| **写者归属** | W-1 专用写线程 / W-2 骑域 worker / W-3 无 OSAL 退化 | 见 §C.2；**取决于 Q-3 的答案** |
| **存什么** | 格式化文本 / 结构化记录 | Zephyr 的 FCB 争辩显示：存原始参数省空间但 `%s` 会丢串（除非有字典）。**我们 push 给的是文本，落在被验证过的一侧**（B-1.3） |
| **满了丢谁** | 覆盖最旧（黑匣子）/ 丢新 | 黑匣子语义应**覆盖保旧新**；但注意 NVS 类实现默认"报错"（B-2.5-5） |

| **现场暂存区结构** | 单条 slot / 多条 slot + ECC | 建议**多条 slot**（容忍连续两次崩溃）；ECC 为可选增强（B-3.1、B-3.2） |

### D.3 对 §A.5 五个待定项的建议

| 问题 | 建议 | 理由 |
|---|---|---|
| **Q-1 分区尺寸/位置** | 取 **16K 扇区整数倍、≥4 块**（例如 4×16K = 64 KB 起步） | §A.6 结论 2；如容量不够，优先**换外置 SPI NOR**（寿命 ×10）而不是抠算法 |
| **Q-2 文本 vs 结构化** | **V1 存格式化文本**（现状接口即可），记录头只放 `len/seq/CRC` | 业界多选文本侧；结构化需先解决字符串驻留（B-1.3）；真要按模块筛选时再走 §C.1 的 T-2 接口扩展 |
| **Q-3 无 OSAL 形态** | 建议**编译期裁掉**（`OM_LOG_ASYNC=0` + `OM_FLASH_SYNC_ONLY` 时持久化后端不参与构建） | W-3 的"只在 flush 点写"会让掉电窗口等于整个缓冲，与黑匣子语义冲突（§C.2） |
| **Q-4 panic 转存是否 V1 做** | **V1 只留接缝**（接口 + 免清零段的预留），转存本体另立项 | §A.7 的成本是每板 4 文件 × 2 板 + 双工具链验证；且两条业界依据（NuttX/Nordic）都把它当独立子系统 |
| **Q-5 导出通道** | 先定**协议形态**（请求带 `ofs`+`count`、完成判据 = 收满声明长度、同时只允许一个未完成请求），通道后置 | 传输无关是旧稿的合理部分（C 节）；协议形态直接照抄 ArduPilot（B-3.5），把导出状态全留在主机侧 |

### D.4 与旧稿的关系（呼应 Part C）

- **被业界证实**：裁决 5（panic 不直写）——两条独立一手依据；裁决 8（顺序轮转天然均衡）——从寿命公式得到证实；裁决 1（隐式扇出后端）——与 Zephyr 的后端模型同构。
- **需要重估**：裁决 6（专用写线程）——器件层已有 worker，且回调内可再提交（§C.2）。
- **被调研推翻的隐含假设**：旧稿把"片内 flash"当作容量与寿命都够用的介质；实际是**容量先卡住（64 KB ≈ 最近 800 条），寿命随后也卡（1 条/s 下约 3 个月）**（§A.6）。
- **业界整体状况**：这个需求**在成熟框架里没有被解决**——Zephyr 的黑匣子后端需求 issue 自 2020 年 open 至今，FCB 后端被关闭；我们能照抄的是**零件**，不是整体（B-1.5）。

## Part E. 两个架构问题的调研答复（2026-09-16）

### E.1 持久化后端该直接依赖 partition，还是依赖"有掉电保护与磨损管理的存储服务"？

**业界事实：两者都不是。业界那个"存储服务"本身就是日志后端要成为的东西——它是兄弟实现，不是下层。**

| 框架 | 分层事实 | 出处 |
|---|---|---|
| **Zephyr** | FCB / FS 后端**直接坐在 `flash_area`（分区层）上**：FCB 自己调 `flash_area_read/write`，空间不足时自己 `fcb_rotate()` **擦最旧扇区**——**环形轮转（即磨损管理的实现）在日志后端内部，不在它下面**。评审意见也是"用 dedicated flash area for logging"（专用分区），不是"再垫一层" | B-1、B-4.3 |
| **ESP-IDF** | NVS 官方称 "includes flash wear levelling **by design**"（126 条目/页 → 擦除次数降 126 倍）；`wear_levelling` 组件**只服务 FATFS**（块转换壳），不是通用层 | B-2 |
| **RT-Thread** | FAL（分区层）→ EasyFlash / FlashDB **各自实现**磨损平衡与掉电保护。FlashDB 基类 `struct fdb_db` 里放的是 `lock/unlock` **函数指针（要求调用方提供互斥）**与 `oldest_addr`（环形锚点）——**它自己就是那个服务** | B-2.1 |
| **横向小结** | 原始报告原话："真正把掉电安全做扎实的是 EasyFlash / FlashDB / NVS 这类**存储库**"——它们是**兄弟，不是上下层** | `raw/research_2_rtos.md` |
| **Linux** | 唯一接近"通用管理层"的是 UBI（磨损均衡 + 坏块 + 原子卷更新），但其存在动机是 **NAND 的坏块与大擦除块**；我们是 NOR，**NOR 不需要坏块管理**（Infineon/Microchip 均明确）⇒ **没有引入 UBI 式通用层的理由** | B-4.5（A5 节） |

**结论**：

1. **日志后端直接依赖 partition + 器件层**，自己实现记录格式 / CRC / 环形轮转 / 恢复扫描——**它就是那个"提供掉电保护与磨损管理"的层**，与 NVS / FlashDB / EasyFlash **同级**，不是它们的消费者。
2. 这**不是**"我们先凑合、以后再抽层"，而是与业界收敛形态一致：成熟框架的"服务"**全是领域专用的**（NVS 的 126 条目页、FlashDB 的 KV/TSL 双形态、littlefs 的 metadata pair），共性只在事后才看得出来。
3. 与本仓既有纪律**互相印证**：`storage_landscape.md` §6.4「不发明存储统一层」+「持久化日志后端将来声明'流式追加后端'窄接口（append/读回/重来/断点）」——**正是本节结论**。
4. **有一块薄能力值得记账、但不在现在上提**：块级擦除编排（erase-ahead）、擦写失败降级 / 失败扇区跳过——任何环形或追加存储都要重复实现。等第二个消费者（bootloader meta / 配置 KV）落地再回头看是否上提（记入演进表）。

### E.2 写者归属：成熟框架怎么做？

**业界事实：主流是「日志服务拥有线程，后端借用该线程执行 I/O」——后端几乎从不自建线程。**

| 框架 | 写者归属 | 出处 |
|---|---|---|
| **Zephyr** | `CONFIG_LOG_PROCESS_THREAD` 建**服务内部的日志线程**；FS 后端用 `LOG_OUTPUT_DEFINE(..., buf, MAX_FLASH_WRITE_SIZE)`（256 B 对齐缓冲）写，并在 `LOG_BACKEND_EVT_PROCESS_THREAD_DONE` 时 `fs_sync()` ⇒ **后端在日志线程上下文里写，按块、可让出** | B-1 |
| **Zephyr（无线程形态）** | 允许 `log_thread_set()` / `LOG_INIT()` / `LOG_PROCESS()` 由**用户显式驱动** ⇒ **业界对"没有专属线程"的答案是"应用显式泵"** | B-1 |
| **RT-Thread ulog** | 异步线程（栈 1024 / 优先级 30 / 缓冲 2048）或 idle hook；官方警告**需要挂起的后端（Flash/网络）在 idle 里可能不可用** | B-2 |
| **NuttX syslog** | **没有线程**——输出在调用者上下文；中断级输出直接丢弃（除非开中断缓冲） | B-2 |
| **EasyFlash / FlashDB** | 纯库，**写者归属交给调用方**，只要求外部提供 `lock/unlock` | B-2 |
| **ESP-IDF NVS** | 同步 API + 内部锁，**无线程** | B-2 |
| **Linux pstore** | 内核侧无专属线程：ramoops 在 panic 上下文写、pstore-blk 用轮询 I/O，之后由 userspace 的 systemd-pstore 接手 | B-3 |
| **ArduPilot** | 写由 `_WritePrioritisedBlock()` + `periodic_1Hz()` 这类**周期泵**驱动（块后端是显式环形缓冲） | B-3.5 |

**我们与业界的关键差异（两条，都会改变结论）**：

1. **我们的器件层是"异步优先 + 每设备一个 worker 线程"**（`hal_flash.c:381`，栈 3072 B），而**业界设备层全是同步 + 内部锁、零线程**（差距分析 G-08 已记）。若照抄"日志线程直接写"，路径上会变成**两个线程**（日志线程 → 域 worker）——这正是 G-08 说的"同一件事两处承担"。
2. **我们的 log 服务从不调用 `backend->flush`**——实测：全仓 `->flush(` **零调用点**，也没有 `om_log_flush` 公共 API；`OmLogBackend.flush` 声明为"可选：强制刷出"，但**是一根未接线的钩子**（唯一在树后端 RTT 直接把它置 NULL）。⇒ **今天持久化后端只拿到 `push`（与 `panic`），没有任何"周期泵"**——"借用日志线程写 flash"在当前实现下**没有触发时机**。

**三方案对照（结合上述事实）**：

| 方案 | 与业界关系 | 代价 |
|---|---|---|
| **W-1 后端自建写线程** | **与业界主流相反**（业界后端不建线程） | 器件层已有 worker，再建即**第三个线程**（+3 KB 栈量级） |
| **W-1′ 借用日志线程**（= 业界形态） | **贴合主流**；但**先决条件是给服务接一个周期泵** | 改动小：把已声明的 `flush` 钩子接线（日志线程 drain 循环里按水印/超时调用），或提供 `om_log_flush()` 公共 API。**顺手补齐了业界都有的 flush 语义**（ulog 的 `ulog_flush`、NuttX 的 `sc_flush`），我们的服务目前缺这一环 |
| **W-2 骑器件域 worker（自时钟链）** | 无先例（业界无此形态） | 占用共享 worker、**写期间读被拒**（`pal_flash_dev.h:210-211`）、设备级 done 回调是**单槽** |

**倾向：W-1′**。它同时统一了两种裁剪形态——**有线程时服务泵，无线程时应用泵**（`om_log_flush()`），后者正是 Zephyr 无线程形态的既有做法，也直接回答了 §A.5 的 **Q-3**。

**先决条件（需记账）**：给 log 服务接线 `flush` 属于**服务侧改动**（`log.h` 公共 API + `backend.c`/`core.c` 调用点 + README 契约），应作为持久化后端立项时的**前置任务**，而不是后端实现里的私活。

## Part F. 方案讨论记录（W-1′ 落地）

> 2026-09-16 用户拍板 **W-1′**（写者 = 日志线程；后端不自建线程；前置任务 = 给服务接线 `flush`）。本节记录定案后新暴露的问题与待决项。**讨论记录，非决策**。

### F.1 定案后的直接后果

1. 写者 = 日志服务的日志线程（异步模式）；**无线程形态（`OM_LOG_ASYNC=0`）由应用调 `om_log_flush()` 泵**——两种裁剪形态统一到同一个原语。
2. 服务需要新增**周期泵**：在 drain 之后调用各后端的 `flush`（契约：单次有界、无事可做立即返回），并新增公共 `om_log_flush()` 作为显式提交点（导出前 / 关机前 / panic 前）。
3. 后端**不建线程**，省下约 3 KB 栈（参照域 worker 的 3072 B），代价是自有 RAM 队列。

### F.2 新暴露的问题：**擦除是同步的，会在日志线程里阻塞**

**事实**：`om_partition_write` / `om_partition_erase_range` 都落到**同步**器件 API（`lib/drivers/src/storage/partition.c:313`、`:329`、`:350` → `flash_write` / `flash_erase`，语义 = "提交 + 阻塞至完成，调用线程睡眠让出"）。分区层**没有异步面**。

**后果**：预擦若在日志线程里做，日志线程会被阻塞整个擦除时长。期间：① 其他后端（RTT/串口）被饿死；② 新消息只能堆在服务消息环（16 槽），满了就是"环满丢弃"。

**定量**（按 §A.6 的 100 B/条口径）：

| 日志速率 | 16K 扇区可写条数/时长 | 若单次擦除 500 ms | 阻塞占比 |
|---|---|---|---|
| 10 条/s | ≈ 160 条 / 16 s | — | ≈ 3% |
| 100 条/s（持续） | ≈ 160 条 / 1.6 s | — | **≈ 31%（不可接受）** |
| 100 条/s（短突发） | — | 服务环 16 槽 ≈ 160 ms 余量 | 突发超过 160 ms 即开始丢弃 |

> **注**：片内 F4 **16 KB 扇区**的擦除时间本轮未取到（datasheet Table 48 的 `t_ERASE16KB`，见 §B-4.5 补注）；已知 128 KB 为 1.3–4 s。**该数值直接决定本节的预算，应先查证。**

**三选项**：

| 选项 | 做法 | 代价 |
|---|---|---|
| **E-1 接受同步擦除** | 仅在"**队列已空且空闲扇区 ≤ 1**"时发起预擦（尽量挑无损时机） | 峰值下仍阻塞并丢弃；需计数可观测。**分层最干净、实现最简单** |
| **E-2 擦除走器件层异步** | 后端持 `FlashDev*`（`flash_find(entry.devName)`）直接调 `flash_erase_async` | 不阻塞；但**绕过 partition 一层**（丢几何校验），且设备级 done 回调**单槽** |
| **E-3 给 partition 加异步面** | 分区层暴露异步擦/写 + 完成通知 | 最干净但改分区层契约——属差距分析 **G-08**"重新评估异步优先"那条线，范围大 |

**正交的降阻塞杠杆（与选项无关，建议一并采用）**：**编程分小块**。片内 F4 `writeUnit = 4 B`、**无页约束**（`bsp_flash_f4.c:57`），因此可按 ~256 B 一块编程（typ 1 ms 量级），**而不是攒满整个扇区再一次性编程**（16 KB = 4096 字，typ 65 ms / max 400 ms 量级）。这把"每次泵的阻塞"压到毫秒级。

**提议**：**E-1 起步**。理由不是"E-1 更好"，而是 §A.6 结论 1 已经要求**落盘范围收窄**（只收 WARN+ 或模块白名单）——收窄后抵达 flash 的峰值率很低，阻塞占比随之落到可接受区间；E-2/E-3 记入演进表，触发条件 = "出现持续高写入率"或"导出与写并发冲突显性化"。

### F.3 泵的契约（需认可）

| 项 | 提议 |
|---|---|
| `flush` 语义 | **单次有界**：最多推进一个工作单元（打包 / 一个编程块 / 一次扇区切换）；无事可做**立即返回** |
| 服务侧触发 | 每次 `log_ring_drain` 之后调用各后端 `flush`（因"无事立即返回"，调用频繁无妨） |
| 公共 API | 新增 `om_log_flush()`：对全部后端广播一次 flush；作为**显式提交点**（导出前 / 关机前 / panic 前） |
| 无线程形态 | 应用周期性调 `om_log_flush()` 泵——**Q-3 由此有了统一答案** |
| 硬不变式 | **至少保留一个已擦扇区待命**（mtdpstore 与 B-4.7 两条独立来源印证）——预擦必须在下个扇区被消耗完之前完成 |
| 不承诺 | V1 的 `flush` 返回 void、不承诺"调用返回即全部落盘"；"排空到底"若将来需要，再加带返回值的 sync 语义 |

**契约改动面**（= W-1′ 的前置任务）：`services/log/log.h`（新增公共 API + 契约注释）、`backend.c`（广播 flush）、`core.c`/`ring.c`（drain 后调用点）、`README.md`（契约与裁剪矩阵）。

### F.4 连带的小需求

1. **后端自有丢弃计数**：`om_log_stats()` 目前只覆盖**服务侧**丢弃（环满 + 参数超限），持久化后端自身的丢弃（队列满 / 写失败 / 擦除失败）需要自己的查询口径——对应 FR-6。
2. **行组装缓冲与超长行截断**：服务给的是 **32 B 段**（`OM_LOG_SEGMENT_SIZE`），后端要自己拼成行；须定义行缓冲大小（建议 128–256 B）与超长行的截断语义。

### F.6 三问的调研答复（2026-09-16）

#### F.6.1 E-1/E-2/E-3：业界**全都用同步擦除**，靠调度纪律把它藏起来

| 实现 | 擦除做法 | 证据 |
|---|---|---|
| Zephyr FCB | `append → rotate`，`fcb_rotate()` **在调用者上下文同步擦最旧扇区** | research_4:157、research_1:386 |
| Zephyr NVS / ZMS | GC 在调用者上下文；ZMS 扇区满时"确认下一扇区为空 → 搬 ATE → 擦 N+2" | research_1:229 |
| EasyFlash ENV | 空闲扇区低于 `EF_GC_EMPTY_SEC_THRESHOLD` **阈值预触发** GC（不等写满） | B-2 |
| FlashDB | `FDB_SECTOR_DIRTY_GC` 标记 + **GC 可续做**（掉电后接着做） | B-2 |
| littlefs | compaction 在调用者上下文 | B-4 |
| ArduPilot block | 环形，`FinishWrite()` 检查"是否要擦掉自己的 header 扇区" | B-3.5 |
| Betaflight | flashfs 在主循环里擦（已知造成循环时间尖峰） | B-3 |

**⇒ 结论：E-1 就是业界形态。** 没有谁在日志后端层面做异步擦除。**但**它们都不是"裸的同步擦除"，而是配了四条调度纪律——**这才是真正该抄的部分**：

1. **始终保留 ≥1 个已擦扇区**：FCB `f_scratch_cnt`、ZMS"始终保留一个空扇区且轮换"、NVS 恒留 1 空页、mtdpstore "ensure at least one zone is writable"、EasyFlash 空闲阈值。**理由原话：保证任何时刻都有可写空间，避免"擦除中掉电"导致完全不可写。**
2. **阈值预触发**（EasyFlash）——不等写满才擦。
3. **懒擦除 / 挑空闲时机**：mtdpstore 只有整块空闲才擦（否则记 `rmmap` 等 flush 时做）；裸环参考实现也建议"空闲主循环后台预擦，避免长擦除卡在实时写入路径上"。
4. **panic 时绝不擦除**（mtdpstore）⇒ 预擦必须在正常路径完成。

**E-2 的真相**：器件级异步**不是业界没做，是驱动层在做**——SPI NOR 擦除器件自持，驱动是"发起 + 轮询 WIP（睡眠让出）+ 完成回调"。**我们的 PAL 器件层已经是这个形态**（`flash_erase_async` + done 回调）。所以 E-2 不是偏离业界，而是"把器件层已有的能力接到日志后端"；代价是要么穿过 partition 层，要么给 partition 加异步面（E-3）。

**修正 F.2 的提议**：E-1 起步**必须与上述四条纪律同时采纳**，否则只是"裸同步擦除"，而非业界做法。

#### F.6.2 各家的分区尺寸与写入策略

| 实现 | 扇区/块尺寸 | 分区尺寸 | 写入策略 |
|---|---|---|---|
| **Zephyr FS 后端** | 文件 **4 KB**（默认） | 10 文件 = **40 KB 起** | 文件轮转、覆盖最老；**被其自家评审判为"对片内 flash 不经济"**（research_1:292/310） |
| **Zephyr FCB** | **= flash 扇区**（要求**连续** `f_sectors`） | ≥2 扇区，其中一个可作 scratch（`f_sector_cnt - f_scratch_cnt < 1` 即 `EINVAL`） | append → rotate |
| **Zephyr NVS / ZMS** | = flash 页 | ≥2 扇区，**恒留 1 空** | 环形扇区轮转 + GC 搬移 |
| **ESP-IDF NVS** | **4096 B/页** | **≥3 页（12 KiB）** | 页轮转 + 条目级回收（擦除次数降 **126×**）；满了**报错不覆盖** |
| **ESP-IDF coredump** | — | 示例 **64 KB** | 单份覆盖，非环形 |
| **EasyFlash LOG** | `EF_ERASE_MIN_SIZE` | ≥2 个擦除单位 | 环形覆盖最旧 |
| **FlashDB TSDB** | `sec_size`（块大小整数倍） | ≥2 扇区 | 索引自扇区头、数据自扇区尾**相向增长**；rollover 覆盖最旧 |
| **pstore/blk** | — | `kmsg_size` 默认 **64 KB**（4 KB 倍数）；**MTD 要求分区 ≥2×record 且 eraseblock ≥ kmsg_size** | 多 chunk 覆盖最老 |
| **ramoops** | `record_size` | `max_dump_cnt` 条 | 环形轮转 |
| **ArduPilot Block** | 页 **4 K** / 块 **64 K** | 整片 dataflash 作环 | 显式环形；写满即停（`chip_full`） |

**三条可提炼的规律**：

1. **扇区尺寸没有"通用答案"，就是"等于介质的最小擦除单位"**——FCB/NVS/ZMS/FlashDB 全部直接用 flash 的扇区/页。用聚合尺寸的只有文件系统（4 KB 文件）与 pstore/blk（64 KB record）。
2. **分区最小值集中在 2–3 个扇区**（FCB ≥2、NVS ≥2 恒留 1 空、ESP-IDF NVS ≥3、EasyFlash ≥2、pstore/blk ≥2×record）。
3. **对我们的含义**：候选 **4×16K = 64 KB** 与 pstore/blk 的默认 `kmsg_size`（64 KB）**量级一致**；而 Zephyr FS 后端的 40 KB 起跳被判"不经济"，是因为它还要存格式化文本与文件名。**64 KB 起步是有业界对照的合理选择。**

#### F.6.3 `t_ERASE16KB`（STM32F427/429 datasheet Table 48）

| 编程/擦除并行位（PSIZE） | 典型 | **最大** |
|---|---|---|
| x8 | 400 ms | **800 ms** |
| x16 | 300 ms | **600 ms** |
| x32 | 250 ms | **500 ms** |

注：**最大值是在 100K 次擦除之后测的**；另 Table 49（带 VPP、0–40 °C）典型 230 ms。

**⇒ 阻塞预算必须按最坏值算**（结合 §D.1-11「绝不用典型值做超时」）：**16K 扇区最坏 500–800 ms**，比我上一轮假设的 500 ms 更差。

**重算 F.2 的定量**（100 B/条、160 条/16K 扇区）：

| 日志速率 | 扇区可写时长 | 擦除占比（典型 400 ms） | 擦除占比（最坏 800 ms） |
|---|---|---|---|
| 10 条/s | 16 s | 2.5% | 5% |
| 100 条/s 持续 | 1.6 s | 25% | **50%（不可接受）** |

**队列/缓冲预算**：按最坏 800 ms × 峰值率计——@100 条/s 需 **≈ 80 条 ≈ 8 KB**；@10 条/s 仅需 0.8 KB。

**两条新的可调杠杆**：
- **PSIZE 是选项字节**：若板子配置为 x8，最坏就是 800 ms；改为 x32 可降到 500 ms。**值得查一下我们的工程有没有设置 PSIZE。**
- **双 bank**：F427 为 2 MB 双 bank，**bank2 起于偏移 1 MB**（`bsp_flash_f4.c:29-39` 的区域表：sector 0–11 属 bank1、12–23 属 bank2）。**若日志分区与代码同 bank，擦除/编程期间取指受阻、CPU 真停转**——此时"让出 CPU"的设计全部失效。⇒ **分区位置应选在与代码不同的 bank**（即利用双 bank 的 RWW 能力）。这条直接约束 Q-1。

### F.7 布局落点 / 介质绑定 / RAM 暂存式写入（2026-09-16 三问）

#### F.7.1 代码占哪个 bank、日志分区能落在哪

**已定案布局**（`multi_strategy_boot_design.md` Q-02，2026-09-07 拍板）：

```
bank1 (1 MB)  ┌ bootloader 64K（4×16K 扇区） ┬ A 槽 = 余量 ~960K
bank2 (1 MB)  └ B 槽 = 1 MB                 ┬ meta 独立区（落点数值未细化）
```

**代码占 bank1**：链接脚本 `ROM ORIGIN = 0x08000000, LENGTH = 2048K`（`rm-a-board/linker/gcc/stm32f427iihx.ld:50`；armclang 侧 `LR_IROM1 0x08000000 0x00200000` 同）——**整个 2 MB 都给了 ROM**，而实测镜像只有 **74.9 KB**（`robot_project.bin`）。所以代码在 **bank1 头部**，远未越界。

**四条真机实测（`flash_dev_design.md:175`）**——比 datasheet 更该用于预算：

| 项 | 实测 |
|---|---|
| **16K 扇区擦除** | **~260 ms** |
| 128K 扇区擦除 | 1059 ms |
| 4 KB 写 | 16 ms（⇒ 256 B ≈ **1 ms**） |
| 64 KB 写 | 255 ms（⇒ 16 KB ≈ **64 ms**） |
| **RWW** | **有效**：擦/写 bank2 时 bank1 心跳全程存活 |

**本项目内部已有同款结论**（`flash_dev_design.md:163` 原文）："**同 bank 擦写仍 stall → staging 放执行 bank 外**"。

**⇒ 对 Q-1 的三条约束**：

1. **日志分区必须放在代码不在的那个 bank（bank2）**——否则擦除期间取指受阻、CPU 真停转，前面所有"让出 CPU"的设计全部失效。**这不是新发现，是本项目已定的纪律。**
2. **片内布局已被 boot 定案排满**（boot 64K + A 960K + B 1M + meta）。要放日志分区就得**从 bank2 里切**（缩 B 槽），即**修改 Q-02/Q-03 的定稿布局**——需与 boot 侧协调（那边另有 agent 在做）。
3. **有充足余量可切**：镜像仅 74.9 KB，B 槽的 1 MB 严重过配；例如 `B = 768K + 日志 256K` 对 OTA 毫无压力。
4. **另**：生产分区表**尚不存在**（全仓只有 `samples/pal/partition/main.c` 定义过 `OmPartitionEntry` 表）——Q-1 的答案将是**第一张真实分区表**。

**阻塞预算按实测重算**（260 ms、100 B/条、160 条/16K 扇区）：@10 条/s 扇区可写 16 s → 阻塞占比 **1.6%**；@100 条/s → 1.6 s → **16%**。服务消息环 16 槽在 260 ms 内可吸收 @60 条/s 以下的流量，更高则开始丢弃（计数可观测）。

#### F.7.2 上层服务是否"只支持 NOR"？

**准确说法：绑定的是「可擦族」契约，不是"NOR"。** 四条隐含假设：

1. 写前必须已擦（显式擦除语义）；
2. 单向写（1→0，擦除态为全 1）；
3. 擦除以扇区为单位、扇区尺寸可查询；
4. **无坏块、无位翻转（写入可靠）** ← **只有这一条是 NOR 特有**。

| 介质 | 是否成立 | 依据 |
|---|---|---|
| NOR（片内/外置） | ✅ 四条全成立 | 本设计目标 |
| MRAM / 自动擦 NOR | ✅（ER-1：erase 缺省 → `NOT_SUPPORTED`） | `partition_table_design.md` §5 |
| **NAND** | ❌ 第 4 条不成立 → **必须独立面**（坏块/ECC） | ER-2；`storage_landscape.md` §6.5「裸 NAND 几乎总是伴随管理层出现」 |
| 随机器件（EEPROM/FRAM） | ⚠️ 分区表不并入（改"命名窗口"） | ER-3；`partition_table_design.md` §5 |
| 块设备（SD/eMMC） | ⚠️ 由 disk/FS 层承担，但**同一窄接口可由另一实现承载** | ER-5；`storage_landscape.md` §6.4 |

**业界对照**：成熟存储库同样是"薄介质抽象 + 族内/跨族实现"——FlashDB 的 `struct fdb_db` 用 union 同时支持 **FAL 裸 flash 与文件模式（POSIX 目录）**；littlefs 的 block device 接口可跑 NOR/NAND/SD/RAM/文件；Zephyr 在传统 flash 上推 NVS、在 RRAM/MRAM 上推 ZMS。

**真正的风险不是"绑定 NOR"，而是这些假设现在既没写下来也没被测过**（partition 不做隔离 ⇒ 假设是隐式的）。**便宜的补救**：把上述四条写成后端的「介质契约」清单，并用**已有的 host 仿真后端 `flash_sim`** 加两个变体去测——① 免擦介质（erase 返回 `NOT_SUPPORTED`）②擦除/写失败注入（对应差距分析 G-10）。这样"只支持 NOR"就从隐含假设变成**被测试的契约**。

**换个问法更准确**：上层声明的是介质无关的窄接口（append / 读回 / 重来 / 断点）；介质差异落在"**这个窄接口由谁实现**"——这正是 `storage_landscape.md` §6.4 的结论。

#### F.7.3 "先存 RAM、水位/周期触发落盘"——这是主流，不是特例

| 实现 | RAM 暂存与触发 | 出处 |
|---|---|---|
| **Zephyr** | DEFERRED 模式消息先入 RAM（`mpsc_pbuf`），日志线程消费；FS 后端 256 B 缓冲 + `PROCESS_THREAD_DONE` 时 `fs_sync()`；**`CONFIG_LOG_PROCESS_TRIGGER_THRESHOLD` = 水位触发**（缓冲条数达阈值唤醒） | B-1 |
| **RT-Thread ulog** | 异步模式 RAM 缓冲（默认 2048）+ 输出线程；`ulog_flush()` 供 hardfault | B-2 |
| **ArduPilot** | RAM 写缓冲 + `LOG_FILE_TIMEOUT=5` s + `LOG_MAV_BUFSIZE=8` KB | B-3 |
| **systemd-journald** | 写入有 fsync 节流（`SyncIntervalSec` 默认 **5 min**），**但 CRIT/ALERT/EMERG 无条件立即 fsync** ← **级别触发的例外** | B-3 |
| **Telegraf** | `metric_buffer_limit` 10000 + `buffer_disk_sync` | B-3 |
| **Android logd** | RAM 环形 + logcatd 落盘（256 MB / rotate 1024 KB） | B-3 |
| **NuttX** | `CONFIG_SYSLOG_BUFFER`（崩溃冲刷"尚未实现"） | B-2 |
| **pstore/ramoops** | **极端形态：RAM 本身就是介质**，配合复位后转存 | B-3 |

**它们这么做，理由与我们的四条一一对应**：① 摊薄介质成本（页编程/擦除批量做）；② 把生产者与介质延迟解耦（调用侧成本恒定——我们的 push 必须在 ISR/生产者上下文快速返回）；③ 让丢失窗口**有界且可预期**（= 队列深度，对应 NFR-5）；④ 给"崩溃时冲刷"一个明确钩子（`ulog_flush` / `sc_flush`）。

**配套的两条纪律**（缺一不可）：
- **级别例外的立即刷**（journald 的 CRIT/ALERT/EMERG 无条件 fsync）——我方对应 FATAL/panic 路径；
- **必须有 flush 原语**——ulog 官方承认异步模式在 hardfault/断言时会丢日志，`ulog_flush()` 就是为此存在。**这正是 W-1′ 要接线的那根钩子。**

**没有"纯直写"派**：介质太慢，且调用侧不能等（ISR/生产者上下文）。**也没有"纯缓冲不落盘"派**：黑匣子语义要求窗口有界。⇒ 我们 Part F.3 提的"RAM 行组装 + 待写队列 + 水位/超时泵"**就是这个主流形态**，需要钉死的是**水位/超时取值**与**级别例外清单**。

## Part G. 决策记录

### G.1 不在片内 Flash 做持久化后端（2026-09-16 用户拍板）

**决策**：持久化后端**不做在片内 flash 上**；等真实外部介质（SPI NOR / EEPROM / SD）到位后再落地实现。

**连带作废的约束**（本稿前面为此做的推导大部分不再适用）：

| 原约束 | 状态 | 说明 |
|---|---|---|
| §F.7.1 日志分区必须落 bank2、与代码分 bank | **作废** | 不再使用片内 flash，XIP stall 问题不存在 |
| §F.7.1 需从 bank2 切、改动 Q-02/Q-03 定稿布局、与 boot 侧协调 | **作废** | **协调成本归零** |
| §A.6 结论 2「分区取 16K 扇区整数倍且 ≥2」 | **作废** | 外置 W25Q 是 **4 KB 扇区** |
| §F.6.3 `t_ERASE16KB` 500–800 ms / 实测 260 ms | **作废** | 外置 NOR 4 KB 扇区擦除 **45–100 ms typ / 400 ms max** |
| §A.6 结论 1「落盘必须收窄到 WARN+」（容量硬约束） | **降为优化项** | 外置 16 MB ≈ **16 万条** @100 B；@1 条/s 可存 **44 小时** |
| §A.6 寿命预算（片内 10k 次 → 64 KB 约 3 个月） | **大幅放宽** | 外置 **100k 次**/扇区 + 容量 16 MB ⇒ 寿命不再是约束 |

**新出现的设计点**（外置 SPI NOR 特有，片内没有）：
1. **256 B 页编程**是主要性能杠杆（片内 F4 是 4 B 字编程、无页约束）——多条记录应合批到同一页；对应差距分析 **G-05** 记的 "`pageSize` 定义了却无消费点"。
2. **erase suspend**（`tSUS` 20 µs）外置支持——擦除期间可挂起服务读，片内没有这个能力。

**仍然有效、且现在是唯一的开工项**（与介质无关）：

| # | 项 | 为什么现在做 |
|---|---|---|
| P0-a | **窄接口**（append / 读回 / 重来 / 断点） | 介质差异落在"谁实现"，接口不定则介质来了要返工 |
| P0-b | **记录格式**（magic/len/seq/CRC + 提交标记 + 记录不跨块） | 同上；且它是导出工具与离线解析的事实源 |
| P0-c | **RAM 介质后端** | 业界有先例（NuttX RAMLOG / Linux ramoops）；让全部介质无关逻辑可在 host 验证 |
| P0-d | **故障注入台**（擦除失败 / 位翻转 / **掉电点截断**） | 差距分析 **G-10** 原文："掉电一致性是存储子系统头号难点，当前无任何自动化手段验证"；**三种介质都需要它**，且用户已定：验证台归存储系统 |

### G.2 未决：先等哪个介质（**它决定后端形态**）

⚠️ **关键分叉**——"后端直接依赖 partition"这条结论**只对可擦族成立**：

| 候选介质 | 族 | 现状 | 对该决定的影响 |
|---|---|---|---|
| **外置 SPI NOR** | 可擦族 ✅ | 无后端（**G-04**） | **现有设计（环形 + 磨损 + 记录格式）直接适用**，只差一个 BSP 后端 |
| EEPROM / FRAM | 随机器件族 ⚠️ | **ER-3** 留口 | `partition v2` **不覆盖**（该族走"命名窗口"，`partition_table_design.md` §5）；需先落 ER-3 层；免擦 ⇒ 环形轮转退化、记录格式可简化 |
| SD 卡 | 块设备族 ⚠️ | **ER-5** 留口 | `partition v2` **不覆盖**；需 ER-5（+ 可能 FS）；后端形态变为"文件追加"（与 ArduPilot 文件后端同形） |

⇒ **若目标是外置 SPI NOR，则本稿的结论全部平移有效**；若目标是 EEPROM/FRAM 或 SD，则**先决条件是先落对应的族层**（ER-3 / ER-5），后端形态也要重定。

## Part H. P0 交付：窄接口与记录格式（草案，2026-09-16）

> 用户拍板：**先等外置 SPI NOR**；**现在先定接口与记录格式**（P0-a / P0-b）。本节为草案，供拍板。

### H.1 介质变化该在哪一层被屏蔽（回应"是否依赖 partition"）

**先把"变化"拆开**——一个持久化日志里，介质相关的只有四件事：

| # | 介质相关 | NOR | EEPROM/FRAM | SD |
|---|---|---|---|---|
| 1 | **擦除单位**（多大、多久、是否免擦） | 4 KB 扇区 | **免擦** | 不暴露（FTL 内部） |
| 2 | **写单位**（最小粒度、页边界、能否原地覆写） | 1/4 B，**256 B 页** | 1 B，可覆写 | 512 B 块 |
| 3 | **读单位** | 无约束 | 无约束 | 512 B 块 |
| 4 | **可靠性**（ECC/坏块） | 不需要 | 不需要 | FTL 内管 |

**介质无关的是**：记录格式、环形/追加逻辑、游标与最旧锚点、恢复扫描、导出迭代。

**⇒ 所以屏蔽的位置是「介质接缝」，而不是"再垫一个通用存储层"。** 日志层只认"**块 + 几何**"：

```c
/* 介质接缝：只暴露"块读写擦 + 几何"。免擦介质把 erase 实现为 no-op */
typedef struct OmLogMediaGeom {
    uint32_t capacity;     /* 可用字节数 */
    uint32_t eraseUnit;    /* 擦除单位；0 = 无擦除语义（EEPROM/FRAM） */
    uint32_t writeUnit;    /* 最小写单位（1 / 4 / 256…） */
    uint32_t pageSize;     /* 页编程边界；0 = 无页约束（片内 F4） */
    uint8_t  erasedValue;  /* 擦除态字节值（NOR = 0xFF） */
} OmLogMediaGeom;

typedef struct OmLogMedia {
    OmRet (*read)   (void *ctx, uint32_t off, void *buf, size_t len);
    OmRet (*program)(void *ctx, uint32_t off, const void *data, size_t len); /* 目标须已擦 */
    OmRet (*erase)  (void *ctx, uint32_t off, size_t len);                    /* 免擦 → 直接 OK */
    const OmLogMediaGeom *geom;
    void *ctx;
} OmLogMedia;
```

**业界先例（都是这个形态，不是我们的发明）**：littlefs 的 **block device 接口**（`bd_read/bd_prog/bd_erase/bd_sync` + config 里的 `read_size/prog_size/block_size/block_count`）；FlashDB 的 `struct fdb_db` 用 **storage union** 同时支持 FAL 裸 flash 与 POSIX 目录，几何由 `sec_size`/`max_size` 带入；Zephyr 的 `flash_area` + `flash_area_get_sectors()`/`flash_get_parameters()`（**几何是通过抽象暴露的**）。

**⇒ 关键发现：我们的 `partition v2` 恰好缺"几何"这一半**——`OmPartitionHandle` 只给 `(reg, index)`，`OmPartitionEntry` 只给 `(name, devName, offset, size)`，**没有 eraseUnit/writeUnit/pageSize/erasedValue**（这些在器件层 `flash_geometry()` 里）。所以今天的日志后端若直接依赖 partition，**必须绕过它去 `flash_find(devName)` 取几何**——这正是你感觉到的那个"依赖不对劲"的地方。

**两条可选解法**：

| 解法 | 做法 | 代价 |
|---|---|---|
| **A. 给 partition 补几何暴露**（推荐） | `om_partition_open` 时把设备几何一并填进句柄（**open 期本来就在做几何校验，成本几乎为零**），或加 `om_partition_geometry(h, ...)` | 改动已交付的 partition v2（PR #23 / Issue #75 范围内）——需走评审 |
| **B. 日志层自己接介质接缝** | `OmLogMedia` 作为日志后端内部的接缝；可擦族实现内部持 `OmPartitionHandle` + 自己取几何 | 不改分区层；接缝私有，将来若要上提需再议 |

**倾向 B 起步 + 记 A 为演进**：理由是 §6.4 的纪律「**先有真实消费者再抽象**」——目前日志是唯一消费者，把它做成公共层就是投机抽象。等第二个消费者（boot meta / 配置 KV，两者都需要"擦除单位"）出现，再把"块+几何"上提。

> **修订（2026-10-01）**：本节"partition v2 缺几何"的结论**已不适用**，「解法 A（把几何填进句柄）」**已否决**——投影字段全部可由句柄已有的 `FlashDev *` 推导，多存一份即多一份无法被强制的一致性义务（见 ADR-0026 修订注记）。现形态：句柄持有 `FlashDev *`，新增 **`om_partition_dev_geom(h)`** 提供经域校验的器件几何查询、**`om_partition_capacity(h)`** 提供分区容量。**"必须绕过 partition 去 `flash_find(devName)` 取几何"不再成立**，故本节的 A/B 选择随之作废——日志层直接 `om_partition_dev_geom()` 即可。

### H.2 记录格式（草案）

```
块（= 一个擦除单位；SPI NOR = 4 KB 扇区）
┌──────────────────────────────────────────────────────────┐
│ 块头 (16 B)                                              │
│   magic32="OMLG" | ver8 | pad8 | seq32 | hdr_crc16 | pad16│  ← 首写；全 1 = 块未使用
├──────────────────────────────────────────────────────────┤
│ 记录 0 │ 记录 1 │ … │ 擦除态填充                          │  ← 追加；不跨块
└──────────────────────────────────────────────────────────┘

记录（头 16 B，对齐 writeUnit）
┌────────────────────────────────────────────────────────────┐
│ seq32 | len16 | rsv16 | crc32 | commit32 | payload[len]     │
└────────────────────────────────────────────────────────────┘
   commit32 = "COMT"(0x544D4F43)  ← **最后写**：只有它被写成精确值，记录才有效
   crc32 覆盖 seq+len+payload
```

**六条格式纪律**（每条都有业界出处，见 §B-4.3 / §B-2.2）：

1. **记录不跨块**——pw_kvs 的理由："跨扇区则擦一个会毁掉该条目"。代价是单条上限 < 擦除单位（4 KB 扇区下留 4 KB，对几十~几百字节的行绰绰有余）。
2. **提交标记最后写**，且**用"需要清特定位"的常量**（不是全 0）。
   - 半写检测：NOR 只能 1→0，撕裂写不可能恰好产出 `"COMT"` 这个精确值（同 MCUboot `boot_flag_decode` 只在精确等于 `0x01` 时判 SET）。
3. **记录级 CRC-32，块头 CRC-16**——§B-4.6 的期望漏检计算：2 B 代价换 5 个数量级可信度。
4. **序号用序列算术比较**（`(int32_t)(a-b) > 0`），32 位先磨损坏而非回绕（pw_kvs 同款）；**块头 seq 决定"哪个块最新"**（Zephyr FCB 也是比 ID 不比地址）。
5. **块尾/空白用擦除态区分**——扫描到擦除态即写游标；不持久化任何读/写指针（§B-4.3）。
6. **CRC 不覆盖会被"只清 0"推进的字段**（学 NVS 的页头 CRC 排除 State 字段）——本项目 V1 若无此字段则无影响，但**格式里留了这个位置**（`rsv16`）。

**可选（V1 不做，留接缝）**：自描述格式表（ArduPilot FMT 思想：分区开头写一条字段表，导出工具无需编译期信息即可解析）；"干燥收尾"哨兵（Betaflight 的 `'E'`，一个字节区分"正常结束 vs 异常掉电"）。

### H.3 介质契约（四条假设 + 怎么测）

后端对介质提出四条假设，**必须写下来并测**（§F.7.2）：① 写前必须已擦；② 单向写（1→0）；③ 擦除以 `eraseUnit` 为单位；④ **无坏块、无位翻转**（唯一 NOR 特有的一条）。

**测试载体 = 故障注入台**（P0-d，G-10）：在 host 上用一个可注入故障的介质实现，遍历掉电点（截断第 N 次写）、擦除失败、位翻转。**三种介质都需要它**，且用户已定验证台归存储系统。

### H.4 本节待定项

1. **H.1 的解法 A（给 partition 补几何）还是 B（日志层私有接缝）**——倾向 B 起步。
2. **块大小**：外置 SPI NOR 是 4 KB 扇区；但**块 = 一个擦除单位**还是"若干个擦除单位组成的更大逻辑块"？（更大块 = 更少块头开销与更少擦除，但恢复扫描更慢、覆盖粒度更粗）
3. **单条记录上限**（超长行截断语义）——建议 256 B，与 `OM_LOG_SEGMENT_SIZE`(32 B) 的组合关系待定。
4. **序号宽度**：记录级与块级都用 32 位？（§B-4.7-4 的序列算术在 32 位下安全）

## Part I. 方向调整：先建底层设施，后建消费者（2026-09-16 用户判断）

> 用户判断："Bootloader 已经在设计当中了，有真实的多消费者了，也就是说现在就开持久化日志服务是错误的，应该先去开发底层设施。"

### I.1 同意方向，但要先切准"底座"是什么

**两个消费者的实际需求对照**（均取自本仓已定案文档）：

| | **boot meta**（K-05 / §3.3） | **持久化日志环**（本稿 Part H） |
|---|---|---|
| 形态 | **固定大小 entry**（seq + 状态 EMPTY/PENDING/VALID + 指针 + 回退计数 + CRC） | **变长记录流**（seq + len + CRC + commit + payload） |
| 语义 | **最新即真相**（读一个 entry 就够） | **环形覆盖保新**（要历史） |
| 轮转 | **双份（或三份）轮转**，新状态写进空 entry，旧 entry 延迟擦除 | 块级环形轮转，覆盖最旧块 |
| 掉电手法 | 半写 entry 因 **CRC 失败被忽略** | 半写记录因 **commit 标记未写**被忽略 |
| 写入频率 | 低频（每次启动/升级几步） | 高频（持续追加） |
| 磨损形态 | **热点位置**（同一逻辑位置反复写） | **顺序环天然均匀** |

**⇒ 共享的是"原语"，不共享的是"策略"**：

| # | 共享（= 底座） | 依据 |
|---|---|---|
| 1 | **介质接缝 + 几何**（eraseUnit / writeUnit / pageSize / erasedValue） | 两者都要；§H.1 |
| 2 | **提交原语**：提交标记/CRC **最后写**、单向写（1→0）、**精确值判别**半写 | meta 与 log 是**同一手法**的两种参数化 |
| 3 | **序号 + 序列算术**（取 seq 最大者；`(int32_t)(a-b) > 0`） | K-05 与 §H.2 纪律 4 同款 |
| 4 | **空位不变式 + 延迟擦除**（新值写进空位，旧值延迟擦除） | K-05 原文与 §B-4.7"至少一个已擦扇区"是**同一条** |
| 5 | **扫描判定约定**（有效 / 半写 / 空 的三态判据） | 两者都要靠扫描恢复 |
| 6 | **CRC 覆盖范围约定**（不覆盖"会被只清 0 推进"的字段） | NVS 页头 CRC 排除 State 字段（§B-2.2） |

**不共享（各自实现，不进底座）**：entry 状态机（EMPTY/PENDING/VALID）、环形覆盖与导出迭代、磨损与擦除调度策略——**meta 是热点写、log 是顺序环，策略本来就不同**。

**业界先例（这正是 FlashDB 的形态）**：`fdb_utils.c` 提供**状态表编码/解码**等公共原语，`struct fdb_db` 提供基类（`sec_size`/`max_size`/`oldest_addr`/`lock`/`unlock`），而 **KVDB 与 TSDB 各自实现策略**。⇒ **共享底座 + 每消费者一模块**，不是"统一存储层"。

### I.2 ⚠️ 一个紧急点

**boot meta 正在被另一个 agent 设计**，而 K-05 已经定到"entry 结构 + 双份轮转 + CRC"这一层。**一旦它的 entry 编码锁定，共享窗口就关闭了**——日志侧再落地时，要么迁就 meta 的编码（可能不合适），要么各写一套（就是 I.1 要避免的重复）。

**需要在它落码之前对齐的，只有两件事**（其余都可各管各的）：
1. **介质接缝**（谁提供"擦除单位/写单位/免擦"？分区层补几何，还是各自取器件几何？）——这决定两边**是否**共用一层；
2. **提交原语的编码约定**（提交标记最后写 + 精确值判别 + CRC 覆盖范围 + seq 序列算术）——这决定两边的**格式是否互认**、工具（离线解析/校验）能否复用。

### I.3 但要避免"没有消费者的底座"

`storage_landscape.md` §6.4「**先有真实消费者再抽象**」仍然成立——差别只是**现在消费者够了**。所以底座的正确形状不是"先独立立项、写完再给消费者用"，而是：

> **共同规格（现在定）+ 由 boot meta 先落地验证（它现在就要落码）+ 日志落地时复用已被验证的原语。**

理由：boot meta 是**已有真实排期**的那个消费者；让原语随它长出来，可以避免"写了一个没人用过的层"。这与本项目做 partition v2 的路子一致。

### I.4 对既有工作的影响

| 既有产出 | 去向 |
|---|---|
| Part A（需求分析）、Part B（业界对照） | **转为底座的证据基础**（不浪费） |
| Part C/D（旧稿审计、调研结论） | 同上 |
| **Part H（接口 + 记录格式草案）** | **升级为"底座规格"的第一份草案**（记录/提交原语部分直接可用） |
| Part G（不做片内、等 SPI NOR） | 决策不变（介质仍等外置） |
| P0-a/P0-b（先定接口与格式） | **与本次调整合并**：不再只是"日志的接口"，而是"**共同规格**" |

## Part J. 共享底座调研（2026-09-16）

> 三线并行：S1 共享底座的切分方式 · S2 算法敏捷性与格式演进 · S3 原语"共享还是重写"。**S3 已完成**，S1/S2 待回。

### J.1 S3：四套经典手法"共享还是重写"——**共享不是默认答案**

| 手法 | 各框架现状 | 结论 |
|---|---|---|
| **① 状态表单向位编码** | **唯一被真正提炼过的一项，且只在 FlashDB 内部**：`fdb_utils.c` 四个非 static `_fdb_*`，KVDB 直调 22 处、TSDB 经宏调 6 处，`FDB_STATUS_TABLE_SIZE` 提升到公共头 `fdb_low_lvl.h:18`。而 **EasyFlash 同算法仍是 `ef_env.c` 的 private static**；**同一个 EasyFlash 库内三套手法并存**（ENV 状态表 / LOG 用扇区三字 magic、无状态表 / legacy ENV 第三套） | 提炼可行，但**极少跨库发生** |
| **② 三段式提交**（PRE_WRITE→数据→WRITE） | **概念最通用、实现最不共享**：EasyFlash / FlashDB / NVS 各写各的；**ESP-IDF 的 NVS 与 coredump 同仓零共享** | 概念共享 ≠ 实现共享 |
| **③ seq 选新** | **最分裂**。唯一真共享：ESP-IDF `bootloader_common_select_otadata`（跨 2 组件 3 处调用）。MCUboot 半共享半重写：状态读写共享（`boot_write_status` 被两算法 6 处调用），但 `boot_status_internal_off` **在三个文件各一份且 swap_move 版已真实分叉**。Zephyr NVS **无 seq**，靠环形位置 | 可共享的是**决策函数**，不是布局 |
| **④ 三态判定**（有效/半写/空） | **重复度最高**：5 个框架 5 套判据（状态表值 / 状态表+数据区 0xFF 探测 / CRC8+位置 / magic 扫描 / 状态字节初值） | 与各自格式强耦合 |

**反向与演进证据**：

- **EasyFlash → FlashDB 是教科书式提炼**（提宏、去 static、魔数换常量）——**但旧拷贝没删**：恢复函数逐行同源、连 TODO 都一起复制（`ef_env.c:1718` vs `fdb_kvdb.c:1598`），且**两个库都继续维护**。
- **MCUboot 是成功的提炼先例**：2019 年提炼出 `swap_misc.c`，2025 年第三个算法直接复用。
- **公开讨论几乎只有一例**——Zephyr PR #103244（把 NVS 归入 KVSS）：反对理由是 **"API similar but not equal... could create unwanted coupling"**，且该 PR 被指流程错误、被迫加回兼容头（#104052）。
- 「同一 bug 各修一次」的公开案例**未找到**（该线 WebSearch 额度耗尽，已标注未证实）。

**⇒ 对我方的分层启示（按耦合度切）**：

| 类型 | 共享？ | 例 |
|---|---|---|
| **纯决策函数**（无状态、与布局无关） | ✅ 共享 | 如"取 seq 最大者"（照搬 `select_otadata` 的签名形态） |
| **与几何无关的提交动作** | ✅ 共享 | 见下条纪律 |
| **记录布局 / 字段偏移** | ❌ **不共享** | MCUboot **刻意保留三份**，因为差异是真实的 |
| **恢复的补偿动作** | ⚠️ **共享回调契约，不共享判据** | 判据与各格式强耦合 |
| **扫描三态判定** | ❌ 不共享 | 5 框架 5 套，重复度最高 |

**两条纪律（比"共享什么"更重要）**：

1. **提炼了就删旧拷贝**——EasyFlash/FlashDB 的双份同源代码是活的反面教材。
2. **把"提交标记最后写"写成跨消费者的文档化不变式**——它是"半写可安全忽略"的**唯一理由**；代码复用拦不住有人把顺序改成先写标记。

**⚠️ 这一节修正了 §I.1 的一处说法**：我把"扫描三态判定"与"提交原语的编码约定"一并列为共享项，**证据不支持**——业界重复度最高的恰恰是第 ④ 项。**修正为**：共享"**决策函数 + 不变量文档**"，不共享"**布局与判据实现**"。

### J.2 S1：共享底座的切分方式——**边界是"薄"，不是"高"**

> 275 行，含事实/对照表/反例/启示/存疑，每条附 URL。

**① 共享层的稳定边界 = 「地址窗口 + 几何 + 边界检查 + 错误上报」，不含磨损/CRC/原子性。**

| 框架 | 共享层给了什么 | 缺什么 / 代价 |
|---|---|---|
| **Zephyr `flash_area`** | 只有 `fa_id/fa_off/fa_size/fa_dev`，**无几何** | 文档自承 read/write 有 "same limitation regard read-block alignment and size as wrapped flash driver"。**代价有源码级证据**：littlefs 适配层注释原话 `/* There's no flash_area API to implement this, so we have to make one here. */`，被迫用 `flash_page_foreach()` 取分区内最大页当 `block_size` |
| **ESP-IDF `esp_partition`** | 只有 `erase_size` | **其新版 BDL（`components/esp_blockdev`，v6.x）补齐了 `write_size/erase_size/recommended_*` 与 `default_val_after_erase`**，README 自陈无共享层的代价是 "a lot of duplicated code and makes it difficult to add new filesystems" |
| **Linux `pstore/zone`** | **最贴近我方需求的样板**：对介质只要 `read/write/erase/panic_write` + `total_size`；用 **`-EBUSY`（稍后重试）/ `-ENOMSG`（换下一区）** 表达坏块 | 策略全在上层 |

**② 反例（本线最有价值的部分）**：

- **Linux 官方判定通用 FTL 失败**：原文 "it is a rather difficult task to create a good FTL layer and **nobody still managed to implement one for Linux**"；`mtdblock` "in many cases … a very bad idea"。
- **Zephyr UBI RFC #109286（2026-05）被撤回**：维护者要求改投 Disk Access，理由是 "**adding additional block interface in parallel to it brings in fragmentation among subsystems**"；并指出 UBI 与 NVS/ZMS 职责**互斥**。作者主动关闭。
- **Zephyr 放弃"泛化 NVS"，改为新写 ZMS**：Alternatives 节承认 "once expanding NVS was identified as suboptimal"。
- **EasyFlash / FlashDB 同作者印证边界**：`ef_utils.c` **只有** `ef_calc_crc32`；ENV 与 LOG **状态机完全不共享**（LOG 连 CRC 都没有）。FlashDB 只共享位状态表 / CRC32 / init / 对齐写，**扇区布局与遍历在 KVDB 与 TSDB 各一份**；且 `FDB_WRITE_GRAN` 是**编译期全局**（反面教材）。

**③ 对我方的直接映射**：

1. **缺的四项几何（`eraseUnit/writeUnit/pageSize/erasedValue`）恰是 BDL 的同构物**（`erase_size/write_size/block/default_val_after_erase`）⇒ **应补齐，且必须是运行期、每器件**（我们 PAL 的 devName 多器件使 FlashDB 式编译期常量不可行）。
2. **但回收策略不要上移**：boot meta（留最新一份）与日志环（留最新 N 条）**语义不同**；底座只提供"擦一个单元 / 写一个单元 + 擦除值 + 坏块错误码"。
3. **`erasedValue` 必须支持 `0x00`**（BDL 显式支持两种）。
4. **原子的标准表述可直接引用**（littlefs DESIGN.md）："Atomicity … requires two parts: **redundancy and error detection**"。
5. **PAL 的"写必须让出 CPU"在成熟框架中无对应物**——它们是同步签名、异步性由 `sync` 回调表达 ⇒ **勿把异步性塞进分层契约**（与 §C.2 的结论一致：异步是器件层实现细节，不是上层契约）。

**⚠️ 勘误（本线证伪我此前的说法）**：我曾在 §E.1 与 Part F.7 中称"UBI 是 NAND 专属、对 NOR 无意义"。**一手文档证伪**：NOR 下只是坏块预留被忽略，**磨损阈值官方明确说对 NOR 也 OK**；真正把 FTL 限定在 NAND 的是 Zephyr 的 Dhara（`CONFIG_DISK_DRIVER_FTL`）。**该说法作废**——但不影响 §E.1 的主结论（不引入通用管理层），因为支撑它的另三条论据（Zephyr flash_area 之上各库自持、ESP-IDF 的 wear_levelling 只服务 FATFS、FlashDB/EasyFlash 同作者印证）**独立成立**。

**未覆盖**：NuttX / U-Boot / RT-Thread / `fal` 自身文档（该线 WebSearch 配额耗尽）——"失败案例是否更完整"存保留。

### J.3 S2：算法与校验该不该沉淀——**能切开的四层**

> 报告 70 KB+（MCUboot / AVB / UEFI / TUF / UBI / UBIFS / littlefs / 对照表 / 演进拒绝 / 启示）。

**答案不是"沉淀/不沉淀"的二选一**，而是四层，每层都有跨框架的一致先例：

| 层 | 沉淀进底座？ | 依据 |
|---|---|---|
| **纯函数实现**（`crc32(data,len,seed)`、将来的 `sha256_*`） | ✅ **该** | 零策略零状态。**不沉淀的代价是复制粘贴**——Zephyr 的 NVS/FCB/ZMS 各自实现 CRC |
| **算法 ID 的登记表与命名空间** | ✅ **该，且越早越好** | 两个消费者各自发明 ID 语义，将来无法统一、无法优雅拒绝。先例：MCUboot `IMAGE_TLV_*` 分族 + 厂商保留段；AVB 整数枚举集中维护；UEFI GUID 命名空间 |
| **"未知/不支持"的语义与错误码分层** | ✅ **该** | "格式不兼容"（整体拒绝）与"记录校验失败"（局部丢弃）**必须用不同错误码**，否则消费者无法正确降级。先例：UBI 的 `-EINVAL`（版本）vs `UBI_IO_BAD_HDR`（CRC）；UBIFS 的 `-EINVAL` vs **`-EUCLEAN`** |
| **谁在什么时机用什么强度** | ❌ **不该** | 这是消费者的格式决策。先例：UBIFS `no_chk_data_crc` 挂载项、Zephyr `CONFIG_NVS_DATA_CRC`、littlefs 用**磁盘版本门控**而非用户配置 |

> **一句话**：沉淀「**纯函数 + ID 登记 + 未知语义 + 错误码分层**」，不沉淀「**谁在何时用多强**」。
> **判据：如果这个决策换一个消费者就可能变，它就不属于底座。**

#### 三条直接可用的改法

**改法 1（最重要）：算法 ID 放"环头/区头"，不要放"每条记录"。**
调研中**没有任何成熟框架把算法 ID 放在每条记录级**——MCUboot 在镜像级（TLV 区）、AVB 在镜像级与分区描述符级、littlefs/UBIFS 在超级块级；UBI 看似"每 64 字节头"，但那是**每 128 KiB PEB 的冗余常量**，且其 version 检查是致命的。
⇒ 我方：**日志环的算法 ID 落环头/分区描述符，meta 的落 meta 区头**；记录级**只留 digest 本身**。
⇒ 代价与反例：不支持"同环内不同记录用不同算法"——**没有框架支持，且 UBIFS 的经验说明"混合"要引入第二套兼容性声明**。**除非有明确需求，不要为它预留。**

**改法 2：把"未知算法"的行为写进契约，区分三种情形**（照抄 AVB + edk2 的三分法）：

| 情形 | 行为 | 错误码要求 |
|---|---|---|
| **格式版本不认识** | **整体拒绝**，且在**读任何字段之前** | 专属错误码 |
| **算法 ID 已登记，但本构建未选入该实现** | **拒绝**，但与上一情形**用不同错误码** | 运维要能区分"这设备没编进 SHA-256"与"这数据来自未来版本" |
| **记录级 digest 对不上** | **只丢弃该记录**，继续扫描 | 坏点只影响当前块尾部 |

**三者都是 fail-closed 的肯定式检查**（"这条记录可信吗"），**都不得降级为"通过"**。

**改法 3：三处判定语义**：

1. **有效性判定必须是合取**——MCUboot 的 `boot_flag_decode` **只在精确等于 `0x01` 时判 SET**，擦除态走**单独分支**判 UNSET，其余一切字节判 BAD。⇒ 我方"这条记录有效"必须是 `magic == 常量 && crc 通过` 的合取，**任一不满足都不得当成"已提交"**。
2. **`seq32` 必须用序列号算术**（`(int32_t)(a-b) > 0`），**不能用裸 `>`**——littlefs 明确要求（`lfs_scmp`）。**这是一条纯收益、零代价的修正**，直接适用于 meta 的双份槽轮转与日志的块头 seq。
3. **提交标志的物理对齐**：MCUboot 专门调整 trailer 结构让 `pad+magic` **落在闪存最小写入区内**（源码注释逐字说明：`boot_magic_off()` 返回的 magic 起点不是写边界，直接写会失败）。⇒ 我方**提交标志自身及其写入必须落在一个闪存写单元内**，否则会出现"标志写了一半"——而这正是记录级校验要防的东西。

#### 三条约束（完整性 vs 真实性）

1. **CRC 不提供真实性，必须写进文档**——CRC 是线性的，攻击者改数据后可重算。应在 ADR 里显式声明"记录级 CRC 用于掉电/位翻转检测，**不提供防篡改保证**"，否则未来的人会误以为"过了 CRC = 可信"。
2. **真实性的正确拼装路径**（照抄 AVB 三层）：记录级 CRC（高频、局部）→ 区级/环级摘要（一次性、小数据）→ 镜像/元数据签名（一次性、绑密钥）。**不要让慢算法做高频工作**。
3. **引入算法升级必须同时引入单调计数器**（AVB `rollback_index` / MCUboot `IMAGE_TLV_SEC_CNT`）——否则攻击者回退旧镜像即可绕过全部新算法。**且要用独立的安全计数器，不是 `image_version`**（后者是给人看的语义版本，可能因回滚 bugfix 而回退）。

#### 一条来自 git 的红线

git 用同一个 SHA-1 同时承担"内容完整性"和"对象名"，换算法的代价是十年迁移（格式扩展 + 翻译表 + 放弃 shallow clone/alternates 互通 + 长期双格式共存）。

⇒ **记录级 CRC 不得成为**：记录的唯一 ID 或索引键（`seq32` 已是天然顺序键，保持它）· 去重/内容寻址依据 · 与外部系统交换的标识符。
**只要 CRC 只做校验、不参与定位，它就永远可替换**——这正是 MCUboot/AVB 能轻松换算法的原因。**建议在底座头文件里对此写一句显式注释**，因为"用 CRC 当记录 ID 省 4 字节"是个很自然但不可逆的错误。

**补记（该线被中止前已落盘的部分）**：

- **ESP-IDF `esp_coredump` 是"校验算法可配"的真实先例**：`choice ESP_COREDUMP_CHECKSUM`，`default ESP_COREDUMP_CHECKSUM_CRC32`，而 `ESP_COREDUMP_CHECKSUM_SHA256` **`depends on ESP_COREDUMP_DATA_FORMAT_ELF`**——即算法选择与**数据格式**耦合（SHA-256 只在 ELF 格式下可选）。**且上游后来把 CRC32 选项删掉了**（收敛到单一算法，而非越配越多）。
- 另一条可引用成本差异：官方 Kconfig help 明说 "SHA256 method needs more **stack space** than CRC32"（1300–1800 字节量级）——**是 RAM 成本差异，不是时间成本差异**。
- **明确缺口（报告自述，勿当结论）**：Cortex-M4 上 **CRC32 vs SHA-256 的吞吐数字未取得**（AN4187/RM0090 抓取失败 + WebSearch 配额耗尽）。该线**拒绝把推测写成事实**，故不给数字——**需要补做**。
- Zephyr NVS 的 CRC 分层小节未补（线程被中止）。
