# OM 项目管理原则

> 状态：v0.1
> 适用项目：Jira `OMR`
> Owner：Bamboo
> 最后评审：2026-11-10

本文件只定义**稳定的机制与规则**。

当前工作主线、状态、字段、字段选项、版本、活跃 Epic，一律以 **Jira `OMR`** 为准；仓库不复制这些内容，避免漂移。

## 1. 核心模型

```
工作主线（Workstream）
  └── Epic（有边界、有目标版本）
        └── Story / Task / Bug（可执行任务）
              └── Subtask（实现步骤）

工作主线 / 模块 / 芯片平台 / 运行环境 = 字段
版本 = Fix Version
```

术语：

- **工作主线（Workstream）**：长期战略分组。
- **状态流转（Workflow）**：Jira 状态机。
- **Epic**：有边界的交付物。
- **Issue**：可执行任务。
- **模块**：架构层 / 代码位置。
- **版本**：发布里程碑。

## 2. 工作主线

- 工作主线是长期战略分组，不是 Epic，也不是 Jira 状态机。
- 数量保持少（建议 3–7 个），便于聚焦。
- 每个 Epic 只归属一个工作主线。
- 工作主线可以暂时没有活跃 Epic；**不建占位 Epic**。
- 当前工作主线集合见 Jira 的 `工作主线` 字段选项。
- 新增、删除、改名工作主线走变更流程。

## 3. Epic

Epic 必须同时满足：

- [ ] 有明确 owner
- [ ] 有目标版本（Fix Version）
- [ ] 有可验收的成功标准
- [ ] 有至少一个可执行的首个 Issue
- [ ] 能在目标版本内收口
- [ ] 不是“目录名”“架构层”或“长期方向”

规则：

- 架构层用 `模块` 字段表达，不用 Epic 表达。
- 不建占位 Epic；未来想法放 Backlog 或文档。
- 完成后关闭；每月 review，合并或关闭过时 Epic。
- 命名格式：`<成果描述>` 或 `[工作主线] <成果描述>`。

## 4. Issue

| 类型 | 用途 |
|---|---|
| Story（故事） | 可交付功能 / 能力 |
| Task（任务） | 重构、构建、CI、文档等工程工作 |
| Bug（缺陷） | 可复现缺陷 |
| Subtask（子任务） | 实现步骤 |

规则：

- Issue 应是可独立完成和验收的最小工作单元；过大则拆 Subtask 或拆成多个 Issue。
- 不是每个 Issue 都必须挂 Epic；但必须填结构化字段。
- 不建“占位 Issue”。
- 命名格式：
  - Story / Task：`<模块>: <动作> + <对象>`
  - Bug：`[模块] 现象（条件）`
  - Subtask：`<动作> + <对象>`

### DoR（Definition of Ready，就绪的定义）

- [ ] 工作主线、模块、目标版本已填
- [ ] 目标行为 / 接口契约清楚
- [ ] 验收标准可判断
- [ ] 验证方式明确（host / 目标板 / 静态检查）
- [ ] 依赖已识别

### DoD（Definition of Done，完成的定义）

- [ ] 代码合入 `integration`
- [ ] CI 绿
- [ ] host 单测通过
- [ ] 目标板验证通过，记录板卡与固件版本
- [ ] 文档 / ADR 更新
- [ ] 不兼容变更加 `breaking-change`
- [ ] 修复版本已填

## 5. 字段与标签

| 类型 | 放哪里 | 例子 |
|---|---|---|
| 结构化维度 | 字段 | 工作主线、模块、芯片平台、运行环境、版本 |
| 跨切面 / 临时属性 | 标签 | `tech-debt`、`needs-hw`、`toolchain:gcc` |

规则：

- 能进字段的，不进标签。
- 只出现一次的概念，写进描述，不建标签。
- 标签使用统一前缀、小写、连字符；不设默认标签；每季度清理。
- **当前字段、字段选项、标签白名单以 Jira 为准。**

## 6. 版本

- 版本格式：`v<major>.<minor>.<patch>[-suffix]`，遵循 SemVer。
- Jira `Fix Version` 与 GitHub Tag 完全一致。
- 只创建当前版本 + 下一个版本，不预建版本坟场。
- 不兼容变更加 `breaking-change` 标签，并在发布说明中单列。
- 当前版本与发布状态见 Jira Releases。
- 发布流程以 `docs/process/git_version_release_spec.md` 为准。

## 7. 单一事实源

| 内容 | 事实源 |
|---|---|
| 原则 / 规则 | 本仓库 `docs/process/` |
| 当前配置 | Jira 项目设置 |
| 实时状态 | Jira |
| 代码与发布 | GitHub |

规则：

- **链接，不复制。** Jira Docs、项目说明只放摘要和链接。
- 不在两个地方维护同一份规则或配置。
- 配置变化时，只改 Jira 并通知参与者；原则变化时，走 PR。

### 当前信息去哪看

| 内容 | 位置 |
|---|---|
| 工作主线 | Jira `工作主线` 字段的选项 |
| 状态流转 | Jira 看板列 / 项目设置 → 工作流 |
| 字段与选项 | 项目设置 → 工作类型 → 字段 |
| 版本 | Jira Releases 页面 |
| 活跃 Epic | Jira 看板 / JQL |

> 仓库只定义“应该怎么看、怎么改”，不复制“现在是什么”。

## 8. 变更管理

### 原则变更

- 修改本文件必须走 PR。
- PR 描述需说明：改了什么、为什么改、影响哪些流程。
- 合并后更新文档头部的“最后评审”日期。

### 配置变更

配置变更不走代码 PR，但必须留痕：

1. 提案：说明变更内容、原因、影响范围
2. 评审：Owner 确认
3. 修改 Jira 配置
4. 迁移现有数据（字段值、状态、Epic 归属）
5. 通知参与者

常见变更：

| 变更 | 额外要求 |
|---|---|
| 新增 / 删除工作主线 | 迁移相关 Epic |
| 修改状态流转 | 迁移 Issue，检查状态类别 |
| 修改字段选项 | 迁移数据，更新 JQL / 仪表盘 |
| 修改必填规则 | 检查存量 Issue，避免阻塞 |

## 9. 评审节奏

| 频率 | 动作 |
|---|---|
| 每周 15 分钟 | Backlog grooming：分配工作主线 / 模块 / 版本，清理阻塞 |
| 每月 | Epic review：完成的关闭，过时的合并，不建占位 Epic |
| 每季度 | 配置 review：工作主线、状态、字段、标签 |

## 10. 命名

| 对象 | 格式 | 示例 |
|---|---|---|
| Epic | `<成果描述>` 或 `[工作主线] <成果描述>` | `[存储系统] W25Q256JV SPI NOR 与存储器件` |
| Story / Task | `<模块>: <动作> + <对象>` | `OSAL: 实现 FreeRTOS 互斥量后端` |
| Bug | `[模块] 现象（条件）` | `[OSAL] 中断嵌套下消息队列死锁` |
| 分支 | `<type>/OMR-<id>-<slug>` | `feature/OMR-123-osi-mutex` |
| PR | `OMR-<id> <type>(<scope>): <summary>` | `OMR-123 feat(osal): add FreeRTOS mutex backend` |
| 提交 | 包含 Jira Key，推荐 Conventional Commits | `OMR-123 feat(osal): ...` |
| 版本 | `v<major>.<minor>.<patch>` | `vX.Y.Z` |

## 11. 角色与治理

| 角色 | 权限 |
|---|---|
| Owner | 创建 / 关闭 Epic，修改 Jira 配置，维护本规范 |
| Developer | 创建 Story / Task / Bug，更新状态，关联 PR |
| Contributor | 通过 GitHub Issue / PR 参与；由 Developer 转为 Jira Issue |

变更配置和原则的权限归 Owner；其他成员通过提案或 PR 参与。

## 12. 新人 onboarding

1. 阅读 `docs/process/jira_quick_start.md`。
2. 获取 Jira `OMR` 访问权限。
3. 阅读本文件第 1–5 节，理解工作主线、Epic、Issue 的区别。
4. 在 Jira 中查看当前工作主线、看板和字段。
5. 选择一个工作主线，认领一个 `good-first-issue` 或由 Owner 分配任务。
6. 创建 Issue，按第 10 节命名分支和 PR。
7. 与 Owner 过一遍 DoR / DoD。
