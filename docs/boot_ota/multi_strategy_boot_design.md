## 1. 设计目标

**一个 boot 系统，一套决策骨架，支持多种"提交策略"**：

- 提交策略 = 启动时把"待升级镜像变为运行镜像"的动作差异（overwrite / swap / direct-xip / ram-load）。
- 策略由**构建/配置期固定**为 bootloader binary 的单一行为（K-11：运行时不做策略切换——bootloader 薄且确定性）。
- 决策骨架（读 meta → 判状态 → 校验 → 提交 → 启动 → 确认/回退）与提交策略**正交**：换策略不换骨架，换骨架部件不换策略。

参考：MCUboot 以同一镜像格式 + 构建期开关（swap / overwrite / direct-xip / ram-load）支撑全部模式——策略差异被收敛在"提交动作"，而不是整个启动路径分叉。

## 2. 术语

| 词 | 含义 |
|---|---|
| 槽（slot） | 一个可容纳完整镜像的**逻辑启动位置**（如 primary/secondary，或 A/B）。槽是逻辑概念 |
| 介质 | 槽的物理承载（片内 flash、外部 SPI flash……）。介质映射是板适配职责（P-04） |
| 镜像（image） | 自描述二进制：头部契约 + 负载（可选尾部摘要区，K-09） |
| meta | 记录 boot 决策状态的小块存储（K-05：双份轮转 + seq + magic + CRC） |
| 指针 | meta 中"当前应启动哪个槽"的引用（K-04：激活 = 翻指针，不是搬移） |
| pending / confirm / rollback | 状态语义三件套（K-07/K-08）：试一次 / 正式永久 / 回退 |

## 3. 策略无关的固定骨架

### 3.1 镜像头契约（K-09，第一交付物）

最小字段集：magic、**结构版本号**、镜像总长、负载起始偏移（对齐用，解决"槽首部与写对齐错位"——MCUboot image offset 思想）、flags、预留区。头自身带强校验；**头外全部负载**的完整性在激活前完成校验（K-09）。

> 契约是 bootloader 与 app **两个独立 binary 间的 ABI**：复位向量偏移、保留区大小、头布局、meta 布局、确认入口的调用约定，全部由此契约约束并版本化。契约改变必须显式升版本号，旧侧遇新侧结构必须能**优雅拒绝**而非误读。

### 3.2 槽位视图

- 上层只表达"槽 + 指针"（P-04）。
- 槽 → 介质 + 基址的映射由每板 bootloader 适配提供；remap / bank 切换 / VTOR 处理全部在适配内（P-04）。

### 3.3 boot meta（K-05）

- 独立于镜像的小区域；entry 结构：seq、状态字段（EMPTY / PENDING / VALID）、当前指针、回退计数、CRC。
- **双份（或三份）轮转 entry**：新状态写进空 entry（带更大 seq），旧 entry 延迟擦除；半写 entry 因 CRC 失败被忽略。
- 布局决策（份数/落点）见 Q-03。

### 3.4 决策状态机（K-06：intent 先行、每步幂等）

```
上电 → 读 meta（取 CRC 有效且 seq 最大者）
  ├─ 状态=EMPTY            → 校验槽内当前镜像头 → 有效则按指针启动；无效 → 进后门（K-12）
  ├─ 状态=PENDING（试一次）→ 校验 staging 镜像（K-09）→ 执行提交策略（§4）→ 启动新槽
  │                         → 回退计数/窗口开始计时（K-08）
  │                         → app 自检通过后写 confirm → 下次按新指针跑 VALID
  │                         → 计数耗尽或窗口超时未确认 → 自动回退（各策略回退语义见 §4）
  └─ 状态=VALID            → 按指针启动对应槽
```

- 每步先写状态再动手；掉电后重启从 meta 判定"上次到哪、要不要续/退"，不依赖运行期记忆（K-06）。
- 确认语义：app 只能 confirm（或什么都不做），无权直接翻指针/改决策（K-07）。

### 3.5 权力分离（K-13）

| 动作 | 归属 |
|---|---|
| 写 staging 槽（流式写入新镜像） | 下载方：app 内 OTA 服务，或外部下载器经传输通道直写 |
| 标记 pending（"有新镜像待试"） | 下载方（写 meta 的 PENDING entry） |
| 校验、提交（翻指针/swap/overwrite）、回退判定 | **bootloader** |

据此，开工序列步骤 3（OTA 状态机）的边界自然划分：**app 侧 = 传输 + staging 写入 + 标 pending + 自检后 confirm**；**bootloader 侧 = 校验 + 提交 + 回退**。两半通过 meta 契约耦合，不共享代码路径。

## 4. 提交策略矩阵

| 轴 | overwrite | swap | direct-xip | ram-load |
|---|---|---|---|---|
| 槽布局 | 运行槽 + staging（可同介质另区） | A/B 等大 + staging/scratch 语义 | A/B 均可 XIP | 非 XIP 槽 + RAM 目标 |
| 提交动作 | staging 全量覆盖运行槽 | 逐块对调（进度落 meta） | 只翻指针 | 校验后拷入 RAM 启动 |
| 写放大 | ~1×（一次升级） | 2-3× | ~1×（staging 一次） | 1× + RAM 搬运 |
| 回滚能力 | 无（旧镜像已覆盖） | 最强（掉电任意点可续/可退） | 靠启动计数回退（K-08） | 靠启动计数回退 |
| 掉电恢复点 | staging 未校验完 = 视为无效，重来 | 进度在 meta，断点续 | 指针未翻 = 旧镜像仍在 | 同 direct |
| 介质要求 | 任意 | 任意（搬移在 bootloader 语境，运行 app 已停） | 槽可 XIP + remap 支持 | 无 XIP 要求 |
| 启动时间 | 最短 | 最长（先搬移） | 短 | 中（拷贝） |
| 典型场景 | 快速升级、面积紧、可接受"坏则回 bootloader 收固件"（配后门 K-12） | 高可靠、不能丢旧版 | **竞赛双 bank 片内布局的自然选择** | 步骤 4 外部 flash 槽的候补 |

> 观察（MCUboot 取舍轴）：回滚能力 vs 写次数/面积/启动时间。**swap 的搬移成本没有换回竞赛场景的等价值**——手机场景需要"运行中自替换还可断电恢复"，竞赛场景升级由人触发、bootloader 语境提交即可，direct + 启动计数回退是量级更轻的同功能物。具体取舍拍板见 Q-01。

## 5. 决策点拍板记录（Q-xx）

> 2026-09-07 全部拍板。框架定位口径：**通用嵌入式框架**——四策略均为骨架的一等支持面，首实现的选择依据 = 参考板硬件形态 + 骨架正交性验证，不以单一应用场景取舍。决策正文见 ADR-0021 (boot_multi_strategy_skeleton) 与 ADR-0022 (osal_none_bare_metal)；本表为结论索引。

| 编号 | 决策点 | 拍板结论 | 依据 |
|---|---|---|---|
| Q-01 | 默认提交策略；多策略落地方式 | **direct 起步，四策略同骨架**：提交动作正交、构建期开关（单 binary 单策略，K-11）；swap/overwrite 为同骨架后续提交动作按需落地 | K-11；§4 观察 |
| Q-02 | 片内布局 | rm-a/F427：**bootloader 64K（4×16K 扇区）@bank1 头 + A=bank1 余量 ~960K + B=bank2 1MB + meta 独立区**；扇区对齐、无 factory（后门兜底 K-12）。A/B 跨 bank 同时吃 RWW 红利：运行 A 写 B 不 stall（flash_dev_design.md §8 实测） | K-04/K-05/K-12；RWW 实测 |
| Q-03 | meta 落点与轮转份数 | **独立区（与镜像生命周期解耦）+ 双份轮转**（CRC+seq，布局允许再扩）；槽尾（trailer）否决——写时机与 staging 完成耦合，复杂度无对价 | K-05 |
| Q-04 | 镜像校验算法 | **CRC32 起步（沉淀进框架算法库）；校验链可配置**——镜像头带 digest 算法 ID、摘要区按算法预留、校验模块构建期选型（旧侧遇新算法优雅拒绝）；SHA-256+ECDSA 记演进 | K-09；K-17 |
| Q-05 | 镜像头契约收敛形态 | **原则先行：契约单头文件，bootloader 与 app 两个工程 include 同一份**；具体数值（保留区/对齐）随布局实现期定 | 3.1 |
| Q-06 | 确认/回退窗口 | **启动计数 N 次**（N 可配，app confirm 停表；无看门狗依赖；掉电重启计数仍推进）——direct 系自动回退的行业标准（ESP otadata）；swap 落地时回退语义随策略天然获得，骨架不重复造 | K-08；K-18 |
| Q-07 | bootloader 运行时形态 | **裸机直跑（裁剪形态）**——被修复者不能依赖被修复者；生态六方 loader 全裸机；代码与 app 同 API（裁剪落地，见 Q-11/ADR-0022） | K-11；K-16；K-19 |
| Q-08 | 后门通道触发源 | **串口握手起步**（零 OSAL 串口轮询三件套已备）；按键/上电超时等多触发源记演进。**2026-09-07 语义扩展（K-21）**：后门协议按**命令组形态**设计（组 ID + 载荷=镜像 + 块/续传）——为通信/命令服务（services 演进项）的裁剪前身；UART = 第一介质后端，非串口私有协议 | K-12；K-21 |
| Q-09 | 升级下载驱动方 | **两路都留（K-13），bootloader 后门直写先行**（与 Q-08 同通道，服务现场灌固件与防砖）；app 内 OTA 服务归步骤③ | K-13 |
| Q-10 | remap/介质映射接口形状 | **随板适配实现期定**：生态无"remap 框架 API"先例——槽=静态表+跳转（direct 固定 XIP 地址连 remap 都不需要）；bank swap/MMU 为板适配跳转前动作；分区表抽象（P-03）随步骤② 前置落地 | P-04；K-20 |
| Q-11 | （Q-07 衍生）裸机 osal 形态 | **正式 osal-none 端口**：时间/中断面保留 + **同步面保真**（mutex=0/1 互斥开关 + irq_lock 临界、sem=生产消费计数、等待由 idle 刷新驱动——基于 osal 的 sync 组件裸机行为一致）+ **首版单执行流**（thread 创建 NOT_SUPPORTED，async 随 OM_FLASH_SYNC_ONLY 编除）；协作式多任务记演进 | K-16（修订注记）；K-19 |

## 5.1 演进项记录（拍板时挂起，非首版范围）

| 演进项 | 触发条件/归属 |
|---|---|
| swap / overwrite 提交动作落地 | 同骨架第二/第三个提交动作（构建期开关）；远程设备回滚需求（swap）或面积紧需求（overwrite）出现时 |
| SHA-256 + ECDSA 签名链 | 需防恶意固件时；镜像头 digest 算法 ID 已预留、校验模块可配置，契约不动 |
| 后门多触发源（按键/GPIO/上电超时） | 串口握手后门验证后按板型扩展 |
| osal-none 协作式多任务（独立栈 + 显式/阻塞让出 + 软定时器） | 框架裁剪形态的裸机业务需求出现时（XRobot 裸机形态为参考，K-19） |
| **通信/命令服务**（services 层：多命令源识别 + 命令组分发 + 介质后端注册；与 log v4 shell 规划合并） | bootloader 后门命令组协议验证后服务化；boot 组（载荷=镜像）迁入，CAN/USB 等介质后端随服务接入 |
| app 内 OTA 服务 | 步骤③（与版本/校验/元数据规划合并；下载侧经通信服务命令组，介质无感） |

## 6. 与开工序列的关系

- 步骤 1（FlashDev）：本草案的槽/meta 全部消费 FlashDev 几何语义（K-01），不新增设备层职责；FlashDev 落地即满足前置。
- 步骤 2（bootloader 最小工程）：先交付 **3.1 镜像头契约 + 3.3 meta + 3.4 状态机**的 direct 单策略实现（Q-01 起步形态）。
- 步骤 3（OTA 状态机）：按 3.5 权力分离划分两半；app 侧半个与步骤 3 的"版本/校验/元数据"规划合并。
- 步骤 4（外部 flash + 持久化日志）：W25Q 槽经 ram-load（或 XIP 变体）进入本骨架（§4 末行）；持久化日志的磨损环形由存储/日志层承担（P-05），不因本骨架改变。
